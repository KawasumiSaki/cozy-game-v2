# 更新方案（开工 / 收工协议）

> 这套协议的唯一目的：**让每次开终端只需要读两份笔记就能开工**，
> 并且保证做完的事一定被记录下来，不会下次重新发现。

---

## 一、开工协议

1. 读 `01-板块/00-目录.md` —— 知道全局站位和下一步
2. 读目标板块的 `01-板块/<ID>-<名称>.md` —— 拿到交付内容、DoD、代码位置、现有状态、验收断言
3. **不要重读总纲**。只有要改架构时才读 `00-架构总纲/V2.2-技术架构总纲.md` 的对应章节
4. 动手前先跑一次自检，确认基线是绿的：

```bash
D:/privacy/Openclaw/Godot-4.7.2/Godot_v4.7.2-stable_win64.exe \
  --headless --path D:/cozy/cozy-game-v2 --quit-after 4500
```

如果基线不绿 —— **先修基线，不要叠新功能**。

---

## 二、开发纪律（来自总纲 §83 / §84）

每个板块交付时必须回答六个问题，板块笔记里已经预填：

| # | 问题 |
|---|---|
| 1 | 输入是什么？ |
| 2 | State 是什么？ |
| 3 | Solver / Generator 是什么？ |
| 4 | Runtime Node 是什么？ |
| 5 | 如何测试？ |
| 6 | 如何证明没破坏之前系统？ |

第六条的唯一答案：**现有的 headless 断言必须继续全绿。**

### 断言纪律

每个板块至少新增一条**断言**，不是打印。要求：

- 能被判定成 `[OK]` / `[FAIL]`，不是只输出信息
- 尽量**先制造反例再修**（例：ART-09 的相机锁，先证明锁得住、再证明解锁可用）
- 数值要能被独立验算（例：地形三角形 32 m² ÷ 0.0625 m²/格 = 512 格，与程序输出对得上）

## 三、收工协议（**每次做完必须执行**）

按顺序更新下面 **5 个地方**，一个都不能少：

### 1. 板块笔记 `01-板块/<ID>-<名称>.md`
- 状态改成 ✅ / 🚧
- 「现有状态」改成实际结果（不是计划）
- 「验收断言」填进**真实输出**（贴 `[OK]` 那几行）
- 「下一步动作」改成给下一个板块的提示，或写「无」

### 2. 目录 `01-板块/00-目录.md`
- 板块总表里改该行的状态
- **「当前站位」**改为：最后完成的板块 + 下一步
- 若产生新欠债，加进「已知欠债」

### 3. 开发日志 `02-开发日志/游戏开发日志.md`
追加一条，格式见下节。**这是独立于其他项目的日志，不要写进 `06-日常/`。**

### 4. 仓库 `docs/ROADMAP.md`
同步状态表。**Obsidian 是权威，仓库是镜像。**

### 5. 提交
```bash
git add -A && git commit && git push origin main
```
commit message 用英文，结尾带 `Co-Authored-By: Claude Code <noreply@anthropic.com>`。

## 四、开发日志格式

追加在文件末尾，`---` 分隔：

```markdown
## 2026-09-11 · ART-09 固定相机档案 ✅

**做了什么**
- 简要 2-4 条

**关键决策**
- 为什么这么选（含被否决的方案）

**踩的坑**
- 现象 → 根因 → 修法。没有就写「无」

**验证**
```
贴断言输出
```

**欠债 / 下一步**
- ...
```

**「踩的坑」这一节不能省。** 本项目最有价值的记录就是这个：
截止 ART-09 一共踩了 10 个 bug，**其中 9 个是断言抓出来的，手玩发现不了**
（例：二楼楼板完全没有碰撞体、斜坡碰撞体从南侧是堵竖直墙、
"路点走完"被当成"到达了"、遮挡为不跟随的角色淡出）。

## 五、板块状态怎么流转

```
⬜ 未开始
   ↓
🚧 部分完成    ← 记清楚「哪部分做了、哪部分没做」
   ↓
✅ 已完成      ← 必须有断言输出作为证据
```

**不允许直接从 ⬜ 跳到 ✅。** 中间状态要如实写，否则下次会重复劳动。

## 六、什么时候该找 Willow

| 情况 | 处理 |
|---|---|
| 需要拍板美术风格 / 素材 | 停，问 |
| 需要改变操作手感（如相机锁定） | 停，问 —— 并给测试开关 |
| 总纲有硬规则但要改架构 | 停，说明冲突后再动 |
| 纯技术实现、有明确对错 | 直接做，做完报告 |
| 发现总纲与代码冲突 | **先诊断取证**（加探针量出来），再报，不要凭猜 |

## 七、这套协议本身怎么更新

如果发现协议不好用（比如某个地方总是忘记更新），
**直接改本文件**，并在开发日志里记一条「协议调整」。

协议是给人用的，不是给人添麻烦的。
