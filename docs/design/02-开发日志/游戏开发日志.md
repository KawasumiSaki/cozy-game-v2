## 2026-09-11 · §45 生产链：机制做完，活链条走不完 ⚠️

**做了什么**

**这条最有价值的部分：我的检查错了两次，两次都是"绿着测量错的东西"**

   断言在测量自己干的活。

两处都修了（那两个检查现在**快照并还原**它们碰过的东西；探针还原 `produced`）。
**如果我不问"这个绿数为什么是绿的"，两个都发现不了。**

**顺带补了一条容器检查一直缺的断言**：`store` 点**可达**，而不只是被**提供**。
提供和抵达是两件事，而此前只检查了前者。

## 2026-09-11 · §35 物品词汇 + 吃东西需要食物（欠债 15）✅

**先纠正一条欠债**
欠债 15 写的是「吃饭不消耗食物（`eat` 只恢复饥饿值）」。实际 grep 全仓库：
**`hunger` 只在 `npc_state.gd:89` 被增加过，`tick()` 里根本没有 `eat` 分支。**
所以居民会饿到 80 → `critical_need()` 返回 "eat" → 走去坐下 → **永远饿着**，
心情被 `-hunger*0.35` 永久压着。
> 「`eat` 只恢复饥饿值」——它连那个都没有。
> **这是今天第二次"欠债描述本身是错的"**（第一次是"植物不跟着挖地走"，
> 而它们一直是跟的）。方向错了，不只是过期。

**做了什么**
- **按 §35 扩了既有的 `CozyMaterials`，没有另建表**：
  > "不要为建筑材料建立一套孤立库存系统."
  `cozyMaterials` 只被 `get_def`/`has` 访问、**没有任何东西遍历它**，所以扩它是安全的。
  加了 `kind` 字段（`material` / `food`）和第一行食物 `bread`（nourishment 45）。
  `wood` 仍然是墙的造价、箱子的存货、居民背包里的那个 wood。
- **`npc_state._eat()`**：吃东西消耗背包里的食物并按份量回饥饿；
  **没有食物就不回** —— 这才是诚实的约束，也是让容器系统对居民有意义的地方。

**踩的坑（这条最有价值）**
`tick()` 是**每帧**调用的，`game_hours` ≈ 0.003。
天真地写「还饿？吃一个」→ `while` 循环每帧跑一次 →
**一秒吃掉整个粮仓（实测 10 个）**。
所以份量必须**跨帧记账**（`_serving_left`，一个 45 点的面包吃到一半要记住），
并且**序列化**，否则每次读档白送一份。

**验证**
```
[cozyv2] eating: with bread hunger 80->24 (bread 2->0); empty pack 80->84  [OK]
[cozyv2] eating a second of frames: hunger 80->69, loaves eaten 1  [OK]
[cozyv2] item vocabulary: foods=["bread"], wood is food=false nourishment=0  [OK]
```
总计：104 OK / 0 FAIL / 0 ERROR（上一轮 101 → 104），跨进程存档仍通过
（新增的 `serving_left` 没破坏存档格式）

**牙齿验证 —— 注意是哪一条抓到的**
把 `_eat` 换回天真版本（每次调用吃一整个）：
```
eating: with bread hunger 80->39 (bread 2->1)  [OK]                    ← 照样通过
eating a second of frames: hunger 80->1, loaves eaten 10  [FAIL]      ← 只有它变红
```

**单次调用看起来完全合理**（吃 1 个面包回 45 点），只有 60 帧那条看到问题。
和 UI-02 的幂等断言**同一个形状**，正在变成这个项目最可复用的测试范式：

> **每帧跑的系统，必须用每帧的测试。它的每一个单次测试都会通过。**

## 2026-09-11 · A 类收尾：#6 性能半（散布按 chunk 增量重建）✅

A 类最后一条。原来每次编辑都**整场重采样** —— 64×64 m、每米一个候选点，
为了一次只移动几格的笔刷。现在采样结果按 chunk 缓存，编辑只重采样它碰到的 chunk。

**障碍（上一条日志里记的那个）与解法**
`terrain_renderer.rebuild_dirty()` 会调 `terrain.clear_dirty()`，而散布在它**之后**才跑，
所以散布永远拿不到"这次编辑碰了哪些 chunk"。
解法：在 main.gd 里建一张**脏 chunk 台账**，在渲染器消费**之前**记账，
并且**在消费它的那次重建旁边清空**：
> 台账活得比重建久，下一次编辑就会去重采样**错的** chunk ——
> 而结果看起来就是一片普通的植被，只是微妙地不是同一个场。

**关键设计**
- 所有派生量（计数 / 候选数 / 最低高度 / 网格）**全部由按 chunk 的采样重新算出来**。
  单一事实来源，才让"增量重建 == 全量重建"是**可证的**，而不只是**打算如此**。
- 局部索引用**计数**得出，不用世界坐标除：`origin.x + 16.0 + 1.0` 和
  `origin.x + 17.0` 可能在最后一位上不同，而一个落到邻格的采样点
  会滚出**另一个种子**，长出**另一株植物**。

**验证**
```
[cozyv2] scatter incremental rebuild: 1 chunk(s) dirty, 2111 -> 2105 instance(s),
         moved=true, matches a full rebuild=true  [OK]
```
总计：101 OK / 0 FAIL / 0 ERROR（上一轮 100 → 101），跨进程存档仍通过

**踩的坑（这条值得单独记）**
第一版断言用的是**挖地**（`dig_brush`）。结果 `moved=false` —— 挖地只改高度，
而那片区域的植物**没有移动够**让指纹察觉。断言**绿着，却什么都没证明**。

改成 `clear_brush`（草→土，改材质 → 必然改变生成规则）后 `moved=true`。

> 这正是这个项目反复付费的那个失败形状：**一条通过的断言，可能只是在
> 比较两个完全相同的场。** 如果不打印 `moved`，我不会发现第一版是空的。

**牙齿验证**：让 `rebuild_dirty` 根本不重采样 →
`moved=false, matches a full rebuild=false [FAIL]`。

**A 类到此清零。** 剩下的欠债全是 C 类（要 Willow 拍板）和两条 D 类（不该修）。
下一张牌是 §39 物品定义（见 `00-B类-待做板块.md`）。

## 2026-09-11 · A 类还债（2 / 6 高度半 / 8）✅

接上一条，把 A 类剩下的三条清掉。

**#2 地形高度挤出到网格 —— "DIG 真的能挖出坑"**
地形场从 Phase 0 就带着 height，DIG/FILL 会改，**而渲染器完全无视它**：
地面是每 chunk 一张平贴在 y=0 的 `PlaneMesh`，所以挖过的格和没挖过的一模一样。
数字在动，别的都没动。

- 每 chunk 改成 **65×65 的格角网格**，挤出到 `corner_height`（角点取周围至多 4 格的平均）
- 仍然是**每 chunk 一个 mesh** —— doc #61 禁的是 10000 次独立 draw call，不是三角形数
- **碰撞用同一批三角形**做 trimesh，不是对场重新采样一遍。分开采样的两个网格
  迟早会不一致，而这里的不一致就是"玩家站在山体里"
- **外围地面从一整块改成框架**：跨过地形场的那块板会变成每个坑的盖子 ——
  玩家看得见坑、从坑顶上走过去。**那比没有坑更糟，因为它是假的**

**#6 只修了高度那半（有个发现）**
"挖地植物不跟着变"**这条原本就不成立** —— `rebuild()` 每趟都重读地形
（`terrain.material_id_at(x,z)`），材质一直是跟着的。错的只有那个写死的
`Vector3(x, 0.0, z)`。性能那半（chunk 脏区）**没做**，原因记在目录里了。

**#8 轮廓守卫 + 屋顶随房间重生成**
- `CozyOutlineGenerator.plan()` **完全没有校验**。轮廓是一圈闭合的墙，
  自交多边形会画出中途相交的墙，房间检测随后拿到一个非平面的图 ——
  又是 T 型接点那一类失败，只表现为"某个房间悄悄没出现"
- **凹多边形故意不拒**：L 形是正当建筑。凹多边形破坏的是山墙屋顶
  （降级成平顶，doc #31 写明的简化），和"拒绝建墙"是两件事
- `_build_roofs` 原来按**房间 id** 跳过已有屋顶的房间 —— **而 id 在墙移动后是活的**，
  所以房间被改形后，旧屋顶留在已经不存在的轮廓上，而世界里的每个计数、包括
  原有的屋顶断言，全都照样正确

**验证**
```
[cozyv2] terrain surface before digging: y 0.00..0.00 (flat)  [OK]
[cozyv2] terrain after DIG 0.5 m: 316 cell(s), surface y -0.50..0.00, collision min y -0.50  [OK]
[cozyv2] scatter sits on the surface: lowest sampled y -0.50  [OK]
[cozyv2] outline guard: bowtie="the outline crosses itself (edges 0 and 2)" (4 wall(s) planned, refused by the guard), repeated="two points are on top of each other (edge 0)"; L-shape and square allowed=true  [OK]
[cozyv2] roof follows its room: noticed=true, rebuilt=true (roof roof_002 -> roof_003)  [OK]
```
总计：100 OK / 0 FAIL / 0 ERROR（上一轮 98 → 100），跨进程存档仍通过

**踩的坑**
1. **`get_faces()` 每个元素都是顶点，不是"每三个里有一个 Y"。** 我那句注释
   本身就写错了模型 —— 而**编译器当场抓住了它**（`minf() argument 2 should be
   float but is Vector3`）。对比前几轮那些静默失败：类型系统在这里是有用的。
2. 给墙选了个没清过的地（`11,11 is natural (grass)`）—— 地形闸门自己说了原因。
   （这条是上一条日志里的，一并记着）

**最有价值的一次牙齿验证**
把碰撞换成平的、表面照旧挤出：
```
terrain surface before digging: y 0.00..0.00 (flat)  [OK]        ← 挖之前没有这个 bug
terrain after DIG 0.5 m: surface y -0.50..0.00, collision min y 0.00  [FAIL]   ← 只有它变红
scatter sits on the surface: lowest sampled y -0.50  [OK]        ← 植物是对的
```
**第一和第三条照样通过。** 如果我把它们写成一整条"挖地有没有生效"，它会绿着
把 bug 放过去。是**拆分**给了它牙齿。

屋顶那条同理：旧行为下 `roof over room_1_0: style=gable, 4 face(s), ridge=2`
**就贴在 FAIL 旁边照样通过** —— 数量对、样式对、面数对。那一行并排就是这条
欠债为什么能活这么久的全部解释。

## 2026-09-11 · V2-26 存档系统 ✅（并从同一个函数里挖出三个 bug）

**做了什么**
- `CozySaveManager`：JSON 写 `user://world.json`，带版本号，版本不符**直接拒绝**不半读
- 序列化补齐：建筑（墙+**楼板+楼梯**+id 计数器）、世界物体（含**容器内容物**）、地形（修好）、居民
- `_apply_world()`：按 `_ready()` 的同一顺序重建事实，再由各 Generator 重建派生层
- F5 存 / F9 读 ｜ `_check_save_load()`，8 条断言

**入口是这句话**：`CozyBuildingState.to_dict()` 上写着
*"the shape a save file will take (doc #64)"* —— 而**从来没有任何东西调用过它**。
这正是上一块刚写进 INVARIANTS 的「声明了但没有消费者」。
把一个从没跑过的函数塞进真正的序列化器，出来三个 bug：

**坑 1 · 只存墙，丢掉全部楼板和楼梯**
`to_dict()` 只序列化 walls。读档后 **0 楼板 / 0 楼梯**。
最阴的是：**房间数照样对**（房间从墙派生），所以世界看起来几乎正常，
但没人上得了二楼。单帧、肉眼都看不出来。

**坑 2 · `JSON.stringify` 把打包数组静默写成字符串**
`_build` 是 `PackedByteArray`。JSON 不认它，静默转成 String，
读回来是个字符串，赋不回字段。
**而原有的地形往返断言照样通过** —— 因为它在**内存里**往返：
`to_dict()` 交回活的 packed array，赋值成功，断言变绿，磁盘上的文件根本读不了。
> **不经过文件的往返，证明不了任何关于存档的事。**

**坑 3 · `_sync_views` 按 id 匹配却从不回指 `v.state`**
它只在"state 对象永不替换"时等价于按对象匹配 —— 只增删可以，**替换不行**。
读档替换了全部 state 对象，视图还指着旧的，于是 `refresh()` 从**已经不在
`state.walls` 里的** state 读几何。被墙角断言抓住：角上不再响应解算器。
修法两处都要：`_sync_views` 回指后再 refresh；`_sync_group` 按**对象身份**判断
（不加这个判断会在每次 regenerate 时重建全部楼板/楼梯视图，破坏 doc #32 的"局部重建"）。

## 2026-09-11 · V2-14 建筑意图（轮廓 → 结构）✅

## 2026-09-11 · ART-11 Terrain Scatter ✅

**做了什么**
- `CozyArtSeed`（E.21）：`WorldSeed + ChunkCoord + ObjectID + ArtRuleID` 确定性种子

- **概率公式拆两半**

- **biome 派生而不存储**：地面一改 biome 立刻变，不用存档也不会与地形漂移。

**踩的坑**
- **墙的节点在原点**（几何烘进顶点里），所以 `global_position` 会说所有墙都在 (0,0,0)。
  写断言前发现，改为传墙体中点数组。

**做了什么：农业的地基**

**关键决策**

1. **`farmland` 追加到 `ORDER` 末尾，不是插在中间。**
   chunk 存的是**索引**（`PackedInt32Array`），插在 `soil` 后面会把
   `stone` 3→4、`water` 4→5 —— **已有存档的每一格都会读成错的材质**。
   已写进材质表注释：**APPEND ONLY**。
2. **耕地不可建**，而且这条规则**由材质自身携带**
   （`default_buildability: "natural"`），`set_material` 自动应用，**不需要额外代码**。
   理由：你不会在庄稼地上盖墙；要盖就先填回土壤。
3. **链是两步，不能跳。** 在草地上直接耕地 → `touched = 0`，什么都没发生。
   清地和耕地是**两个工具**，这个"什么都不发生"是有意的 ——
   否则清地那一步就是可选的，两条工具名就是同一条链。
4. **不做海拔。** Willow 明确说现在全是平地。`_till_cell` 里**不碰高度**，
   并在注释里写了"这一刀不许偷偷带进海拔编辑"。

**踩的坑**

### ⚠️ 第 11 个工具会撞死快捷键方案

`hotkey_name(i) = str((i + 1) % 10)` —— 注释写着
"Tools are numbered 1..9 then 0, so **ten of them fit a row without a modifier**"。
第 11 个工具会**和第 1 个重复打印 "1"**，`index_for_hotkey` 反查也会错位，
现有断言 `hud tool hotkeys` 立刻变红。

**我没有绕开它，而是扩展了同一套方案**：index 10–19 用 Shift，
显示成 `S1..S9, S0`，并加了 `index_for_hotkey_text()` 作为 `hotkey_name()` 的逆函数
（断言读的是**打印出来的标签**，需要一个能反查的入口，两个函数放在一起才不会漂移）。

### ⚠️ Godot 里 Shift+1 的 `keycode` 是 `KEY_EXCLAMATION` 不是 `KEY_1`

`keycode` 是**逻辑键**（带修饰符），`physical_keycode` 才是**物理键**。
按 `keycode` 匹配数字，**所有 Shift 快捷键会静默失效**。
现在按 `physical_keycode` 匹配（为 0 时回退到 `keycode`）。

### ⚠️ 断言抓到了我自己写的 bug

第一版"farmland 不可建"那条红了，因为我在**耕完之后**才读土壤的可建性 ——
变量名叫 `soil_b`，读到的却是 farmland。

**这正是为什么这条断言要同时检查两半**：只查"farmland 不可建"的话，
它对"可建性整个坏掉"也会通过。

**验证**

## 2026-09-12（八）· Core Architecture V1.0 第 1 项：存档迁移 + 旧档夹具

**Willow 通过提案，四条限制**：不引入 ECS ｜ 不引入 EventBus ｜ 不迁 JSON ｜
**不重写已有系统，只加边界和接口**。执行顺序 ① Save → ② Entity → ③ Resource。

### ① 完成（提交 `6618571`）

**政策写在了常量旁边**（这是重点，不是机制）：

```
加一个带安全默认值的字段   -> 不 bump（旧档照样能读）
改一个字段的含义           -> bump，并注册一步
删一个字段                 -> bump，并注册一步
```

**bump 了却没有注册步骤 = 故障，不是政策** —— 档案变成永不可读。

**机制**：`migrate()` 从档案版本**逐步走到 VERSION**，一步一个 Callable。
v1 到 v3 会跑 v1→v2 再 v2→v3，**每一步可单独测**。步骤返回非字典、或不推进版本，都判为「没有世界」。

**拒绝机制保留**：没有路径的版本**仍然是拒读**，不是硬读一半。
半懂的存档比没有存档更糟，**因为它看起来像是读进来了**。

**`migrate()` / `can_migrate()` 收一个可选目标版本** —— 这不是装饰：
`VERSION` 还是 1，**没有它，整条链永远走不到，机制就是未经验证的代码** ——
正是本项目反复付过代价的形状。

**夹具是真输出**：529 KB，来自 `--cozy-save-on-exit`，带真实段落
（terrain / building / objects / npcs / clock）。
**手写的桩只会测到作者以为的格式。**

**验证**：单元 7 套件 / 38 用例 / **737 检查 / 0 失败**；冒烟 **118 OK**；
跨进程存档仍然通过。

## 2026-09-12（九）· Core Architecture V1.0 第 3 项：Resource Manifest

**提交 `ab37a68`。契约一个字没改**（path in → definitions out → 非法带原因拒绝 → RAW 排除），
**换的是"怎么找到文件"。**

`load_dir` 用 `DirAccess` 走目录 —— 编辑器和 headless 能用，
**导出构建不能用**（没有散落文件可枚举，只有打包资源）。manifest 就是随构建走的那份清单。

- **`scan_paths(root)`** —— **全项目唯一一处走树**。`_scan` 和生成器都走它，两边不可能对不上。
  **排序**不是装饰：`DirAccess` 返回的是文件系统顺序，不排序的 manifest 会因为**与资产无关的原因**churn，
  然后漂移检查会在没人动过的树上失败。
- **`load_manifest(path)`** —— 路径相对于 manifest 自己所在目录，所以文件和它描述的树一起走。
- **`tests/tools/gen_asset_manifest.gd`** —— 构建期生成器，`--script` 工具，不是运行时依赖。
- **manifest 按名字排除自己**，否则它会把自己列进去，漂移检查就成了"集合 vs 自己的超集"，永远不相等。

**过期的 manifest 会被抓到，不会被发布出去。** 失败模式是静默的：
**构建成功，只是里面装错了东西**。加一个定义而不重跑生成器：

```
asset manifest: 5 listed, 6 walked, stale(missing=pixel/props/rock_small_02.json)  [FAIL]
```

还检查**每个列出的文件要么产出定义、要么被拒** —— 两者都没有的文件是在加载器里**消失**了，
那是计数看不见的唯一一种失败。

**注意什么不需要写**：「一个 id 一个资产」**早就是现成的** ——
`_load_file` 从 ART-10 起就在拒绝重复 id 并给原因。

**验证**：单元 **8 套件 / 42 用例 / 751 检查 / 0 失败**；冒烟 118 → **119 OK**。

**踩的坑**：断言第一版引用了 `_check_assets` 里的**局部变量**，跨函数不可见 →
`Identifier not declared`。**修法不是把变量提上去，而是让断言自给自足** ——
改成比对"列出的每个文件都产出了定义或被拒"，这比原来的写法**更强**。

**剩：② Entity Registry**（统一 id + `state_of(id)`，不改 State/View 架构）。
**建议单独一次会话只做它** —— 它会动到存档汇合点（`to_dict`/`from_dict` 现在各系统自己拼顶层键）。

**踩的坑（本轮最大的一个）**

**两个 outline 并排 → 面遍历把两个房间合并成一个，而且不报错。**

`CozyOutlineGenerator.plan()` 会把**每个** outline 封成闭环。两个房间并排时，
共享边就被**各发一遍** —— 同一条线段上两条墙。平面面遍历遇到重复边，
行为是**把两个房间合成一个**：

```
[probe] 1. one room                            seg= 4 room(s)=1 area(s)=[48.0]
[probe] 2. one L-shaped room                   seg= 6 room(s)=1 area(s)=[84.0]
[probe] 3. two rooms, both loops closed        seg= 8 room(s)=1 area(s)=[96.0]   ← 合并
[probe] 4. two rooms, shared edge once         seg= 7 room(s)=2 area(s)=[48.0, 48.0]
[probe] 5. rooms + corridor, both loops closed seg=12 room(s)=1 area(s)=[104.0]  ← 合并
[probe] 6. rooms + corridor, ends dropped      seg=10 room(s)=3 area(s)=[48.0, 48.0, 8.0]
```

**没有任何一行报错。** 按最朴素的实现，整座地牢会变成**一个房间**，
而且看起来完全成功 —— 正是本项目一贯栽的那种"看起来是绿的绿数"。

**修法**：三个 outline 之间的三种关系要分开对待 ——

| 关系 | 处理 |
|---|---|
| 两条边**完全重合**（共享边） | **只发一次**，并在那条墙上开一个门 → 门洞左右仍是两个房间 |
| 一条边**完全落在更长的共线边上**（顶上去） | **丢掉** —— 那是门洞不是墙，长墙已经跨过它了 |
| 两条共线边只在**一个端点相接** | 什么都不做 —— 那是共用一个角，不是通路 |

**"严格更长"这个条件是关键**：它让共享边活下来（两份完全相同的边已被去重合并成一条，
没有更长的边能把它盖住），同时让顶上来的短边被丢掉。

**顺带得到一条更强的结论**：`links` **根本不必存**。
哪两个 outline 相接、接在哪一段，是**几何上可推导的**。
存它就是把推导结果写进文件 —— 而运行时推导出来的那一份永远是对的，两份必然漂移。
（同 `Rooms are DERIVED`。这条要 Willow 点头才改文档。）

### 一、A5 结清：`has_farmland` 为什么读成 false

队列里让我走 `apply_intent(Op.TILL) → _till_cell → set_material`。
**那条路没问题。** 问题在**存档路径**，写探针量出来的

```

after set_material_at(2,2,'water'):  has_water=true   material=water
after chunk to_dict/from_dict:       has_water=false  material=water   ← 旗标丢了，数据没丢
after system to_dict/from_dict:      has_water=false  material=water
```

`CozyTerrainChunk.from_dict` 直接写 `_material`，**从不重算派生旗标**。

**它为什么咬人**：`main.gd:2798` 的 `terrain.from_dict(snapshot)`（在
`_check_scatter_incremental` 里）走的是**活地形**，而 `_report()` 的调用顺序是

和上次记的"0 个播种点"完全对上。

`vegetation_scatter._any_water` → `CozyBiome.classify`；这个世界没有水，
所以它读 false 一直是对的 —— **一个潜伏的 bug，不是不存在的 bug。**

**修法**：`_recount_flags()`（`_init` / `from_dict`）+ `set_material` 里

犁一块地 912 格 × 4096 = 3.7M 次操作，比它要省的那趟走还贵。

**教训和"数错了当 bug 处理"是同一条**：**一个写进文档的测量值，如果没人重跑，
它就是一个凭猜的数字。** 已把队列里那行改掉。

### 三、快路径要有等价性断言，不是速度断言

chunk 快路径只走**含耕地的 chunk 矩形**。它成立依赖一个**本文件不拥有的事实** ——
"只有耕地能长播种点"是 `CozyObjectDefs` 的规则。所以自检里加了：

- **按位置比集合**（不是比数量：两趟数量一样、位置不同，是一株长错地方而不是少一株）
- **查重**（chunk 矩形和 tile 格点不对齐时，同一格会被提供两次 —— 两株作物挤一格是缺陷）

新增：`tests/unit/test_terrain_chunk.gd`（8 例 22 检查）。

1. **风是世界空间噪声场** —— 不是每根草自己抖。阵风是**一个会移动的位置**。
2. **量化帧率 + 每株一个相位** —— 平滑运动在像素风上本身就是错的来源。
3. **旋转轴在根部** —— 我们的 quad 是"抬起半个身高"贴地的，照原样旋转根会甩出地面。

频率极小（约 1/200 m）；**描边在 shader 里长出来**（蒙版不能重画，那是 CC BY 唯一没给的）；
**树不是剪影**（棕树干 + 绿树冠，一个 tint 变不出两个颜色）→ `silhouette` 逐素材。

**差点毁掉像素画的设置**：`detect_3d/compress_to` 默认 `1` ——

所以没有物品可穿，所以没有数字能动，**而所有这些系统的每一个测试都是绿的**。

怪物就是那个源头，而且是最小的那个：**有血、会死、把表滚给杀它的人**。

**pick 表现在能点名一个"定义"**，不只是"类型" —— "随便一把武器"是三把剑，

**断言抓到它自己两次**：
- **第一次它抓的是自己的错**：按住 40 帧数到 2 次命中，看着像 `has_hit` 守卫失效 ——

- **第二次它量到 0**：那一下"按下"被上一段测试残留的收招吞了 ——
  **而收招本来就是干这个的。** 改成先让状态机归位再按。

### 三、`76dec35` · 幻化：**改外观，不改数值**

**整个系统就是一个字段**，因为这个项目已经把它需要的分层做完了：
定义 = 是什么 ｜ 实例 = 你手里那一个 ｜ **外观 = 看起来像什么**。

**放实例上，和词条同一个理由**：两把铁剑是两把剑，**一把幻化成钢剑的样子，另一把不受影响**。
放定义上就是全游戏重涂 —— 另一个功能，而且更差。

**唯一不能破的规则，牙齿报出了那个数**：

```

改坏：让 apply 设 definition_id（经典错误：改"它是什么"而不是"它像什么"）
→ 7 条红，the resolved attack is identical: got 20.093000, wanted 12.093000
```

**那个静默升级被抓住了。**

**时装（以后）不需要特例**：一个没有数值、只用来当外观来源的物品**已经**通过槽位规则，
而且**永远不会让目标变差**，因为目标的数值根本不从幻化读。

**⚠️ 明说了没做**：现在**没有东西渲染穿着的装备**，所以幻化的"图"那一半今天没有消费者。

## 2026-09-15（第七轮）· 地上的物品：三条路改道，以及一个被最短 reach 卡住的半径

**Willow 把"卸下该做什么"答成了一个系统。**

> 我们需要做掉在地上的物品这个东西，比方说右键树，砍树，然后会掉下来木头\*4，
> 打怪会掉下来装备，比方说某个小怪掉落 5% 的几率掉钢剑什么的。**我们靠近自动拾取。**

所以 EQ lane 出第一块**世界机制**：`world/objects/dropped_item.gd`（新实体 kind `drop`）。
**砍树、打怪、（将来的）卸下是同一条路** —— 这才叫系统，不叫按钮的下场。

### 一、一个数比整段规格值钱：半径被**最短的** reach 卡住

拾取半径就是这套机制的全部。太长 → 每个掉落都在出现的那一帧被捡走，
`掉在地上` 和 `直接进包` 变成**同一段代码配两句不同注释**（账本、数字、时刻全一样）；
太短 → 捡东西变像素猎。

**上界来自物体表里最短的那个 reach，不是你正在看的那个。**
`_gather_from` 拒绝在超过 reach 的地方动手，而掉落物落在物体的**边缘**、朝玩家那侧 ——
所以"站在自己 reach 极限上的玩家"和"他刚砍下来的东西"之间的距离**就是那个 reach**。

```
树 / 石头   reach 1.3
作物        reach 0.8   ← 最短的，一开始没看它
```

第一版写 **1.0**，因为眼前那个数是 1.3。后果：**收作物会把小麦直接塞进包，
而砍树会留下东西要走过去** —— 同一套机制两种手感，**而游戏里没有别的东西能分辨**。

抓到它的不是我看屏幕，是**单元套件里那条"对每一个可采集物体"的断言**。
它写得比需要的宽（我当时想的是"万一以后来个短 reach"），结果**现在就有**。
现在 **0.6 < 0.8**。

> **当常数被一张表卡住时，上界是表的最小值；只点名一行的检查，是一个已经停止观察的检查。**

### 二、装不下就留在地上 —— 这是规则，不是体贴

背包有容量、pack 没有，所以**只有一种掉落会被拒绝**。拒绝是
`add_item` 返回 -1，真正重要的是它接下来去哪：
**"收下了又销毁"是玩家唯一会体验成损失的结果** —— 他看见一把剑掉下来，
没地方放，然后它没了，没有解释也拿不回来。

规则：**装得下才拿，账本确认到了才从地上删。**

两种状态断言看不见的错法：拿了但**不删**（下一帧再拿一次 —— 同一把剑，永远）、
装不下却**删掉**（形状是 bug 的沉默）。两条都断言了，两条都做了改坏实验。

**每帧喊一句"装不下"等于没喊** —— `refused` 一个 bool，只置一次，
而且**故意不进存档**：它是"这一局已经说过什么"，不是掉落的属性。

### 三、一次击杀掉 2–3 件，落在同一个点上就是两件看不见的

按表序散在一个**确定性**的小环上（`DROP_SPREAD` 0.36，`count <= 1` 不散）。
随机会让"同一个 roll"不再意味着同一个世界。

⚠️ 环上两件的最大间距 **0.72 > 半径 0.6** —— 有意的，走过去一件一件捡。
**这条把改坏实验打回自己身上一次**：第一版 `_check_fight` 站在第一件上
`_tick_pickups()` 一次就指望捡完，结果 `bag 0 item(s)`、`copper 6`、地上还有东西。
不是系统坏了，**是检查在断言"这个散开没有作用"**。改成逐个走。

### 四、`objects.has(drop)` 不是 `false`，是一个 typed-array 错误

写"它不是家具"那条断言时打了**两行 `ERROR`**，返回值**恰好是**想要的 `false`。

`Array[CozyWorldObject]` 的 `has()` 会拿值去校验元素类型。**"恰好对"是最危险的一种对** ——
`0 ERROR` 是基线的一部分，而那条断言自己看不见。
已记进 `docs/INVARIANTS.md`（bug 27）。修法是改成断"铺一个掉落没有往 `objects` 里加东西"——
那才是真正要问的，而且**类型系统已经保证了另一半**。

### 五、存档：比较要"读回来"，不要 stringify

JSON 把每个整数变成浮点，写出去的 `0` 和读回来的 `0.0` **作为文本不等、作为数字相等**
—— `CozySaveManager` 开头就写着这句话，**还是踩了**。
第一版把一次完全忠实的往返报成 `(CHANGED)`。

修法不是加容差，是把两份 payload 都过一遍 `apply_dict`，
比**两个掉落自己怎么描述自己** —— 那才是要问的性质：**文件读得回来、而且读回来是同一样东西**。

> **序列化往返是关于"两个读者意见一致"的主张，所以要靠读来测。比字节是把写的那一半测了两遍。**

### 六、改坏实验：11 条，**9 条当场红，2 条绿着 —— 而那 2 条才是最值钱的**

| 砍树改回直接写包 | 红（1）＋ **1 行 ERROR** ← 见下 |
| 捡到之后不从地上删 | 红（3） |
| **拾取 pass 不看装不装得下** | **绿** ← 见下 |

**两条绿的都是真发现，而且两条的修法都是加断言，不是改代码：**

**① 外层 `fits_in` 是纵深防御，坏了不丢行为，只丢"说明"。**
`collect_into` 自己也查一遍，所以把 `_tick_pickups` 那句换成 `if false:`，
**掉落照样被拒绝、照样留在地上、腾出空位照样能捡** —— 行为一个字节没变。
那个分支**唯一**产出的东西是一句话。所以断言改成断**那句话**：
被拒绝之后 HUD 消息里要**点出是哪一件**没装下。

> **纵深防御会让外层无法被行为测到。唯一能测它的方式，是测只有它才产出的那样东西 —— 这里是一句话。**

**② 往返比较是**对称的**，所以看不见"从来没写过的字段"。**
把 `to_dict` 里的位置删掉，**两边都加载到原点、完美一致、绿灯**。
单元套件抓到了它，只因为那条断言比的是**它自己放置掉落时用的那个坐标**
（`Vector3(-3.5, 0.0, 8.25)`）—— 一个**常数**，不是一次比较。

```
live   payload 没有 "position"  ->  掉落落在 (0,0,0)
loaded payload 没有 "position"  ->  掉落落在 (0,0,0)   -> 相等，绿
```

修法一行：拿**标记掉落自己的常量** `DROP_MARK_AT` 比。
**和生产链那条是同一个规矩：拿一个被测对象伪造不出来的东西去比。**

```
改坏   冒烟 154 OK / 0 FAIL / 0 ERROR -> 11 条里 9 条红
补完两条断言后重跑那 2 条 -> 2 of 2 caught（11/11）
```

## 2026-09-15（第八轮）· 装备面板 + 背包：格子是**位置**，而两个交换能弄丢东西

Willow 的规格（第五轮给的，这一轮做完）：

> 装备面板和背包最好是可以互动的，就是你在装备面板右键装备可以显示脱下和卸下，
> 脱下就是放到背包里面，卸下就是扔到地上。**现在还不用做角色身上真的穿了装备。**

**一个右栏、两个面板、三个动词。** 它们在同一个 `VBoxContainer` 里，
因为"在一个里脱下、看着它出现在另一个里"就是"可以互动"的全部意思 ——
锚到同一个角会是"一个面板把字压在自己身上"。

### 一、13 个格子来自**身体**，不是来自"手上有什么"

`capacity_of(kind)` 决定格子数，所以**三个护石槽是三个格子、两枚戒指是两个**。
如果画的是"手上有的东西"，那么**空格子就没了** —— 而
**空格子本身是信息**：背包还空着，还是少了一格，是两件事。

而 13 这个数**也是"全画在第一个格子"的画法会产生的数**，所以断言问的不是数量，
是**哪一个**格子收到了剑、哪一个收到了戒指、哪一个还是洞。

### 二、格子显示的是**看起来像什么**，不是**是什么**

`_name.text = item.appearance_name()` —— 幻化过的剑在格子里显示"Iron Sword"，
而 tooltip（`describe()`）说它实际是"Steel Sword"。

**`appearance_name()` 从写出来那天起一个调用者都没有**，它自己的注释写着
"一个在钢剑图上面写着 Iron Sword 的背包，是一份关于谎言的 bug report"。
**面板格子就是它等的那个调用者** —— 又一个"声明了没有消费者"被补上。

### 三、三个动词，两个能弄丢东西 —— 都放在 `CozyPlayerState` 上

只有它同时拥有背包和身体，而这两个交换是**游戏里唯一能让物品"消失"而不只是"出错"**的地方。
两次都不显示在屏幕上，状态**丢完之后还是自洽的**，只是少了一样东西 —— **断言看不出来**。

**① `stow`（脱下）：先问背包、再脱。** 反过来的顺序 —— 先脱、然后发现没地方放 ——
结局是**既不在身上也不在背包里**，玩家看见的只是"我的剑没了"。
所以拒绝是**整块的**：物品**留在身上**，而且**说出来**。

**② `wear`（装备）：顶下来的那件一定能放回去**，因为腾出来的**正是**它要的位置。
这不是运气，**是一条性质** —— 所以从背包里换装永远不可能丢东西。
`equip()` 返回被顶下来的那件就是为了让调用者能决定，这里唯一的决定是"放回去"。

```gdscript
if displaced != null and bag.add_item(displaced) < 0:
    push_error(...)   # 够不到；够到就说明容器和容量表吵架了
```

**写成 `push_error` 而不是返回值**：这里没有"正确地继续下去"的方式。
一件哪儿都不在的物品，是玩家看不见、说不清、也拿不回来的那一种失败。

### 四、卸下要扔到**前面**（`1.4 > 0.6`）

**`TOSS_DISTANCE` 存在的唯一理由**：掉在玩家**自己位置上**的东西**按定义就在拾取半径内**，
下一帧会被 `_tick_pickups` 自动捡回来 —— 那个按钮看起来就是坏的。
扔向**前方**（`camera.ground_forward()`，和 W 键同一个方向）而不是侧面，
因为那是玩家正看着的地方。断言把**两个常数的关系**也钉住了，不只是这一次的几何。

第一版断言写了三句，**两句永远不会失败**：

```
「面板不小于它需要的最小尺寸」  → 恒真：容器不会把子控件摆到最小尺寸以下
「面板装得下它所在的栏」        → 恒真：栏会长大来装下子控件
「都还在窗口里」                → 真的
```

实测：格子 68→88 px，**栏从 300 自己长到 354，前两句照样绿**，
而面板已经跑出 1280 宽窗口 —— **正是这条断言要抓的失败，报的是 `[OK]`。**

**tell 是句子是用什么写的**：那两句在描述布局规则**会做什么**，
而**凡是能从规则推出来的，都不可能是"规则被违反"的证据**。
活的那句**点名一个失败**（"右手边那列格子不在屏幕上"）。

修法留下的两句都能假：**内容需要的宽度超过了这个文件自己声明的宽度** /
**带着溢出整栏跑出窗口**。两条改坏都见红。

> **和「声明了没有消费者」是同一条教训，高一层**：那边是没人读的字段，
> 这边是没有东西能证伪的句子。**两种都是"在场、写得好、只是看起来承重"。**

## 2026-09-15（第九轮）· 尺度统一：一个世界密度，一个为此后退的镜头，和一个 1.75 m 的人

Willow 给了两张表（模块尺寸 + 每类资产的像素密度），并说**"都按照你的建议做"**。
这是 `待拍板-C类` 第 5 条 —— **从 2026-09-11 挂到现在**。

| 定的事 | 数 | 原来 |
|---|---|---|
| 世界像素密度 | **32 px/m** | 60 |
| 默认镜头可见高度 | **22.5 m**，镜头后退 **75 m** | 12 m / 40 m |
| 玩家身高 | **1.75 m** | 1.2 m |
| 角色贴图 | 按 **64 px/m 画**（32×112）、按 32 显示 | 16×24、20 px/m |
| 地面编辑单位 | **保持 0.25 m** | 不动 |

### 一、密度和镜头是**同一个数写了两遍**

```
720 px ÷ 22.5 m = 32 px/m
```

`PIXELS_PER_METRE` 和 `ZOOM_STEPS[2]` 是两个独立常量，**没有任何东西让它们一致** ——
而它们一旦不一致，**全游戏的资产都在错误的放大率上，且没有任何地方会说**，
玩家能给的反馈只有"画面有点怪"。`_check_camera` 现在断言这个除法。

### 二、视野变宽了，**镜头没变宽**

FOV 是从两个数推出来的：`2*atan(可见高度/2/距离)`。
**只把视野放宽会让镜头从 17.06° 变成 31.42°** ——
而**更宽的镜头不是更宽的画，是另一张画**：所有侧面物体的透视压缩都变了，
**而没有一张资产是按那个角度画的**。镜头 40 → 75 m 让角度一模一样。

两条断言，**都从常量算，不读活着的相机** ——
玩家缩放过的镜头会留下一个存盘的 index，读 `camera.fov` 就是在测他上一次的手气。

### 三、一片草是 0.40 m，**因为一片草是 0.40 m**

草的**世界尺寸原本是从像素数推出来的**（`metres_for_pixels(24)`）。
这让 `magnification()` 对它成了**恒等式** —— 永远是 `x1.00`，
而密度报告把那叫"native"，**它不可能说出别的**。

密度一改就现形了：24 px 在 32 px/m 下是 **0.75 m**，草会整体翻倍，
**地面覆盖率从 114% 变成 402%**，而报告**照样写 x1.00**。

修法：把**设计事实和测量分开**。

```
vegetation_scatter.REAL_SIZE   一片草是 0.40 m，因为一片草就是 0.40 m
magnification()                这幅画离那个尺寸该有的密度差多远
```

现在报告说的是 `grass_tuft_01 24px over 0.40m = x0.53` —— **一个真的测量，
有一个真的答案**（这片草该按 13 px 重画），而 `_check_scatter` 断言了
规则注释自己声称的那个覆盖率，所以**删掉 `REAL_SIZE` 会把绿色的 x1.00 变成红色的 402%**。

### 四、角色：占位图**按比例重写**，不是拉伸

旧的 `make_character_texture` 把 16 和 24 **写死在十个坐标里**，
所以把人从 1.2 m 抬到 1.75 m 只能整段重写。
新的一版**每个坐标都是画布的比例**（`_box(img, 0.25, 0.17, 0.75, 0.52, cloth)`），
画布尺寸只有一处（`CozyPixelArt.CHARACTER_TEX_*`），身体从那里读。

**并补上了一条一直只写在散文里的规则**：精灵的世界高度**就是**胶囊高度。
单元测试现在断言它 —— 两个数分开写的时候，不一致**不会报错**，
只是"人高不对"，没有任何消息。

`CAPSULE_RADIUS` **故意没动**：它不是身体尺寸，**它是导航间隙**（`NAV_CLEARANCE` 就是它）。

### 五、改坏实验：7 条，7 条红

| 改坏 | 结果 |
|---|---|
| 密度和镜头不再一致（32 → 60） | 红 |
| 视野变宽、镜头也跟着变宽（75 → 40） | 红 |
| 镜头缩了、密度没跟着动 | 红 |
| 人缩回 1.2 m | 红 |
| 角色表按旧的 16×24 画 | 红 |
| **草的尺寸回到"由像素推导"** | 红 ← 见下 |

**最后一条第一次是绿的。** 删掉 `REAL_SIZE` 之后**没有任何断言看得见** ——
草从 0.40 变成 0.75 m，地面从 114% 变成 402%，而密度那一行**照样打 x1.00**。
**所以要补的不是代码，是一条断言**：把规则注释里那句"地面覆盖率略微超过 100%"
**真的量出来**。补完 → `7.14 tuft(s)/m2 x 0.75 m each = 402% of the ground [FAIL]`。

> **一条在两条边之间自我计算的检查，是穿着测量外衣的恒等式。**
> 和「从画法写出来的检查是恒真的」是同一条，低一层：那边是**从规则推出来的句子**，
> 这边是**从自己推出来的数字**。

### 六、美术模板（Willow 当场要的）

`01-项目/xiansuwd/04-美术模板/`：**16 张画布 × (空白 + 带格子) = 32 个 PNG + `index.html`**。
尺寸**全部来自代码常量**，每张都标明画完放哪、谁读它。

- **四层树**（树干 + 前中后三层树叶，四张同尺寸同轴心）**按要求拆好了**
- ⚠️ 但 **README 第四节写明了代码今天还画不出来的四件事**：

## 2026-09-15（第十轮）· ENV V0.3 风：一个数据源，派生不存储

设计文档：**ENV V1.0 §6 V0.3 —— "一个数据源 + 注入，风格与 clock 一致"**。
它管 `wind_direction` / `wind_speed` / `wind_gust`，影响云 / 雨 / 雪 / 草 / 树 / 叶。

### 一、**从时钟推出来，不存储** —— 这是整个设计

`wind_at(hours)` 是**纯函数**：第 3 天 14:30 的风**永远是同一个风** ——
任何一次会话、任何一次读档，**存档里关于风一个字都没有**。

这正是 `INVARIANTS` 里两条已付代价的 bug 的形状：**存下来的值可以和它派生自的东西不一致**；
**累加出来的值每跑一帧就多漂一点**。而且它让**测试可以直接问"下周三下午什么风"**，
不用跑游戏 —— 那是任何用 `randf()` 自己往前走的系统做不到的。

### 二、**它不弯任何东西**

「一种植物摆多少」是 `WIND_STRENGTH`（关于**植物**的事实，散布 owns）；
「现在多大风」是这个文件（关于**世界**的事实）。**散布在同一个地方把它们乘起来** ——
所以**风停了，树内部的顺序还在**：树干仍然比叶子动得少，而不是树散架。

阵风是**两个不整除的正弦叠加**（一个正弦是"风扇定时开关"）。
风速**永远不到零** —— 场停下来又启动是"有形状的 bug"，不是"风小了"。
**没变就不发信号** —— 每 0.25 秒发一次同样的三个数，是在训练监听者忽略它，
而这里的监听者要重写八个材质。

### 三、⚠️ 这一轮我犯了**三个错**，而且三个都是"本该抓住它的东西"抓出来的

**① `material_of` 我加了一个重复的。** 那文件里**四十行之上早就有**一个。
重复定义让**整个类解析失败**，而它的症状**不是报错** —— 是
**单元测试挂住不退出**（`run.gd` 的守卫判 `== null`，而解析失败的脚本非 null）。
**交接里记过这个坑，我又踩了一次。** 侥幸活下来的那个改成调用 `image_material`，
顺带修掉它少的一个守卫：**重建之后已经被释放的网格**。

**② 活断言比错了对象。** 材质的方向在「大风那一小时」读，而 `wind.direction`
在**时钟恢复之后**才读 —— **拿一小时的对照另一小时的**，把好线报成了断线。
修法是**在读材质的那一刻把它抓下来**。

**③ `bind()` 的参数追加在信号参数后面，不是前面。** 我的接收函数把顺序写反了，
每次发射都失败 —— 而套件把它报成"它从来没说过话"。

> **三个都不是设计错，是"我以为 API 是这样"**。第一个的代价最大：
> **一个重复的函数定义，症状是测试挂住**，而不是"重复定义"。

### 一、收获按**植株**结算，不按动词（`f7c4b09`）

Willow：「**不同的植物 harvest 会产生不同的产物，你逻辑先做好。**」

**它修的是一个静默的错**：`CozyRecipeDefs.for_point()` 返回**第一个**声明了该交互点的配方，
而它是**按 id 字母序**遍历的。所以三株都提供 `harvest` 的植物**解析到同一个配方**，
**其中两株会给出错误的产物，而且哪里都不说** —— 亚麻交出小麦。

**第一版修法给每株植物加了自己的动词**（草 `cut`、亚麻 `pull`）。
那是**同一个坑换更多词汇**，不是"把逻辑做好"，已删掉：
**所有可采集物都提供 `harvest`，由物体自己说出它的配方。**
`for_object(def_id, point_type)` 读交互行里的 `recipe`，对更早的东西回落到 `for_point`。
两个消费者（玩家采集、居民生产）都走它；居民那侧是一行改动，
**因为它干完活时停在的那个节点本来就在作用域里**。

`ambiguous_offers()` 会点名**任何提供某动词、而多于一个配方主张该动词却没说清是哪一个**的采集物，
套件断言它为空。**那条让字母序变安全的规则不是"每个动词只有一个配方"，
而是"两个配方不许主张同一个动词而不说清是哪个"。**

**逻辑本身的断言**：把三株 `harvest` 植物挨个问一遍，
**然后数"光凭动词"能答对几株：至多一株，且不是零株**。
第一版那条**拿一个值和它自己比** —— 一条恒等式，而且是那一轮里的第三条。

同一提交还进了这条链的原料（stick / hay / fibre / rope / cloth）和它的终点
（**一顶帐篷，是 MATERIAL 不是 object** —— 所以"摆下去"仍然是建筑系统的事），
以及它起头的两种采集物：`grass_patch`（3 hay，4 小时再生）、`flax`（2 fibre，8 小时）。

**然后定了离线模型**：「玩家不在线家园也在运行，只是运行效率低，在线 NPC 每小时产出 10、不在线 2」。

**我的调研结论（带许可证）**：「在线游戏 + 保存每个玩家世界」是**三个产品，成本差 ~10 倍** ——
① 云存档（客户端模拟，服务器只是 blob 仓库）→ ② **世界托管/参观** → ③ 权威联机。
**你要的"别人能参观"落在 ②**，而**只有 ① 是"保存玩家数据"**。
**字节数是零头**：delta 存法一个世界 ~100 KB–1 MB，整张 tilemap 是 10–500 MB —— **1000 倍纯属设计选择**，
而本项目的 `Intent → State → Solver → Generator` **本身就产出 delta 的形状**。
**写坏防护的共识只有一条**（Factorio / Minecraft / Terraria / 两个 Godot 插件各自独立收敛）：
**临时文件 → flush → rename → 轮换 `.bak`**；⚠️ **Windows 上 rename 覆盖不保证原子**，
所以真正救你的是那份 `.bak`。**Godot 给传输与复制，故意不给持久化、账号、权威、存档安全。**
许可证：可采纳 **PocketBase(MIT)** / **godot-sqlite(MIT)** / **Pterodactyl 形状(MIT)**；
**Luanti(LGPL) 与 Veloren(GPL-3.0) 不可采纳**（share-alike）。

**⚠️ 而"10 → 2"这句话藏着一个坑，我把它摊开了**：
**产出打折、消耗不打折 ⇒ 离线是净亏，居民会饿死。** 三种做法：**A 离线时世界"时间"慢 5 倍**
（一切自洽，但挂机一天几乎没动）｜**B 离线不模拟居民**（世界时钟照常走、居民不消耗、按速率记账 ——
**一个纯函数，服务器不需要跑 1 万个 sim**）｜**C 离线真跑慢速 sim**（最贵）。
**Willow 选了 B。** B 唯一的风险是"产出有了第二个来源"，**解法是让那个速率从在线那套配方表算出来、
不许写第二个数字** —— 只要速率是**派生的**，B 就不比 A 脏。

### 七、任务 2 停在探针：**原地写会毁档**，而且**我的第一版探针量错了**


**⚠️ 而我第一版探针报了一个假结果**：`rename_absolute` **两次都失败，而且源和目标同时消失**。

```
A/B/C/D 四种写法（正斜杠 / 反斜杠 / DirAccess.open(dir).rename）  err=OK
E. renames onto an EXISTING destination: dst OLD -> 'NEW'  [REPLACED]   ← 承重的那条
```

**所以 `temp → rename` 在 Windows 上可用**，原子替换这条路走得通。

### 八、然后回去做玩法：**存档写安全**（任务 2，代码提交 `d538c7c`）

**老写法是一个会毁档的写法**：`save_world` 用 `FileAccess.WRITE` 打开**活档路径** ——
**它在新世界写入第一个字节之前就把旧世界截断了**。那个窗口里崩一次，
留下的不是"损坏的世界"，是**没有世界**（`load_world` 返回 `{}`）。
**探针造出那个文件**：`a truncated save with NO backup: load_world -> {} (the world is GONE)`。

**现在的顺序**（每一步的位置都是有理由的）：**写 `.tmp` → 把活档改名成 `.bak` → 把 `.tmp` 改名成活档**。
道理是**在每一个瞬间，磁盘上至少有一份完整的世代**：
两次改名之间崩掉 → 没有活档、但有一份完整的 `.bak` —— **所以 `load_world` 会去试它**。

| 崩在哪 | 磁盘上剩什么 | 玩家看到 |
|---|---|---|
| 写 `.tmp` 过程中 | 旧活档完好（＋一个没用的 `.tmp`） | 一切照旧，`.tmp` 被丢弃并说明 |
| 两次改名**之间** | **没有活档，一份完整 `.bak`** | **世界回退一档，并且被明确告知** |
| 第三次改名之后 | 新活档 ＋ 上一代在 `.bak` | 正常 |

**回退不静默** —— `last_source` 记 `main`/`backup`，走备份会 push_warning。
**一个没人知道的回退不是安全措施**：玩家会拿着**落后一档**的世界继续玩，
**而所有检查都通过**，因为检查问的是"世界回来了没有"，不是"回来的是哪一份"。
残留的 `.tmp` 同理：它是**名字看起来很正常**的半成品，所以**丢弃并说明**。

**🔴 顺带挖出 bug 23 的第二次出现。** `_read_doc` 用的是 `JSON.parse_string` ——
**它遇到坏文件会直接打印**，于是"拒绝一个坏档"看起来和"构建坏了"一模一样。
**bug 23 的修法当时只打在副本蓝图上，存档层一直留着老写法**，两天没人发现，
**因为从来没有测试喂过它一个读不了的文件**。第一个这样的测试把单元运行的
`0 ERROR` 变成 `1 ERROR`，**而每一条检查照样是绿的**。

**量出来的两条平台事实**（不是猜的）：
- **rename 覆盖已存在的目标是可用的** —— 四种写法都 OK，而且本项目 `user://` 路径**含空格**。
  但 **Windows 不保证 POSIX 那条保证**，**所以真正的网是那份 `.bak`，不是 rename**
- `FileAccess.flush()` 是 Godot 能给的、最接近 fsync 的东西（**没有目录 fsync**），
  所以断电仍然可能弄丢一份"报告说存成功了"的档 —— **那份 `.bak` 也是为它准备的**

**删掉了 `save_manager.exists()`** —— **没有任何调用方**（本项目最贵的那个习惯），
而"有没有档"这个问题 `load_world` 用返回 `{}` 就答了。

> unshaded billboard is two objects from two different games.**

**"割裂"是已知的。现在的答案是"把 3D 也压平"**（`make_flat_material`，去掉光）——
代价是建筑变成**没有光的纸板**，等于拿一种割裂换了另一种。

> **所以这不是改道，是把那个妥协往上换一档**：不是去掉光，而是**把光风格化到两端共用一种画法**。
> 这条方向**从现状往上走**，这一点值得记下来 —— 它让"要不要动"变得容易回答。

#### 2. 但现实是**四个**资产类别，不是两个

| 层 | 生产者 | 运行时形态 |
|---|---|---|
| 建筑 / 家具 | 程序化或手作 | **真 3D**（现在 UNSHADED） |
| 大树 | Blender 多层同心壳 | **2.5D** |
| 草 / 花 / 小石 | 精灵 | 面片 + 告示牌 |
| **角色 / NPC** | Blender 当**工厂** | **精灵表**（纸片，永远面向相机） |

**"割裂"不只是"3D 建筑 vs 2D 角色"** —— 是**四种生产者做出来的四种东西在同一个画面里**。
要做到不割裂，就是让四类**共用一套画法**（同一套色阶、同一条光照曲线、同一种描边）。
**这比"给建筑描个边"大一圈** —— 但它也是唯一能让画面读成"一个游戏"的做法。

#### 3. 三项各对到哪：**两项不要新决策，一项要**

| 她说的 | 项目里已有什么 | 新决策？ |
|---|---|---|
| **手绘像素风贴图** | **已在待办上**：墙面材质是**程序生成 16×16**（**比规范粗 4 倍**）、**地面是格子着色根本没有贴图**、**家具是把一张图拉伸铺满每个面**（不是平铺）。三条都在 `04-美术模板/README.md` 第四节 | **不要** |
| **三渲二光影** | **就是队列里的 ENV V0.4**；**2026-09-15 她已同意**用 Dylearn 那套（toon ＋ 云影），并要求**草/树/石一起上、不能只照亮草** | **不要** |
| **黑线描边** | **新的**。有先例：**草的 shader 里描边是长出来的**（Dylearn 那套） | **要** |

#### 4. 撞上冻结合同的三处

**① 「角色不是 3D」是冻结合同**（总纲 §1.2 ／ `ART_PROFILE.md` §9 ／ ROADMAP `Locked decisions`）——
**"割裂"正长在这条缝上**。A：角色保持纸片，两端共用一种画法（零结构改动）／
B：角色也做真 3D 三渲二（**作废整条 Blender 精灵表产线** ＋ 美术模板 **8 张角色表**的帧数契约
＋「一个观察方向 = 一套精灵」省下来的钱要重新花）。

**② 「滤镜」正是 ENV V0.1 PixelRenderer，现在是阻塞项** —— 它被阻塞的理由就是"改画风管线"。
⚠️ **而且有个硬冲突**：现在是**原生 1280×720 ＋ 不做全局降采样**（冻结合同），
而**全屏后处理描边在原生分辨率下会画出亚像素宽度的线** —— 和像素风直接顶。

**③ 描边画在哪一层**：**烘进贴图**（**无主之地的实际做法主要就是这个**，黑线画在贴图里 ——
和像素风最合、运行时零成本，**但要她画**）／ **几何描边**（转角清楚，但 **32 px/m 下线条宽度会抖**）／
**后期描边**（**唯一能同时描住纸片角色的办法**，**但它就是 ②**，要先解冻）。

#### 5. 结论：**建议的第一步不需要任何新决策**

**先做 3D 那一半** —— 墙 / 地面 / 家具的**手绘像素贴图（按尺寸平铺）** ＋
**三渲二光照（toon ＋ 云影，草/树/石一起）** ＋ **描边烘进贴图**。

**做完之后"割裂"的两端只剩角色表** —— 那时再决定角色怎么跟，判断会容易得多。

**⚠️ 而且现在做最便宜**：项目刚解冻"可以进真素材"，**目前几乎没有真美术**
（美术模板 16 张画布刚生成、角色表还没画）。**要改尺改画法，现在是代价最低的时刻** ——
和相机 C 是同一个道理（*大部分资产还是占位，现在翻最便宜*）。

#### 6. 卡着的三个问题（要她一句话）

1. **角色：保持纸片（A）还是也做真 3D（B）？**
2. **ENV V0.1 滤镜解不解冻？**（只影响描边走哪条路，**不挡第一步**）
3. **能不能开窗口截图？** —— 这条线**只能靠眼睛验**（`--cozy-shot` **要真窗口**，
   项目规矩是不自动弹 GUI）。不能开的话，节奏就得改成"她开、我按她描述改"

> **这一节不是"没做"，是"没定"。** 三件事里有两件本来就在待办上，
> 所以我**没有把它当新方向搁置** —— 第 5 节那条第一步随时可以开工。
