# 0. 文档定位与当前状态

## 0.1 游戏定位：《无冕之乡》

> **家园模拟（RimWorld）＋ 小队冒险刷宝（Chronicon / 暗黑）＋
> 程序化幻想世界建造（Tiny Glade）＋ 八方旅人式像素立体美术**

**一句话**：白天经营一个会自己运转的村庄；晚上带着村里的某个居民下魔域刷装备；
带回来的东西让村庄更强 —— 而**村庄里的居民，就是你冒险世界的一部分**。

**建造是手段，不是目的。** 这不是一个"点击按钮盖房子"的游戏。

### 四个参照系，各拿一半

| 参照 | 拿它什么 | 明确不拿 |
|---|---|---|
| RimWorld | 居民有需求 / 工作 / 技能，殖民地自己运转 | 不做完整人格、心理与社交模拟 |
| Chronicon / 暗黑 | 单角色刷宝：词条 / 镶嵌 / 掉落 / 鉴定 | 不做开放世界 |
| Tiny Glade | **程序化**生成建筑：模板 + 参数 → 生成 | **不做自由摆砖块** |
| 八方旅人 | 像素美术 × 真实 3D 空间的立体感 | 不做 HD-2D 后期处理 |

### 最大亮点（Willow 2026-09-12 定）

> **基地里的居民，就是你冒险世界的一部分。**

```
培养一个铁匠 → 他制作传奇武器 → 你带着这把武器进入魔域
      ↑                                        ↓
   升级村庄  ←────────  带回稀有材料  ←────────┘
```

**这个闭环把"家园"和"副本"从两个游戏变成一个。** 它是本项目区别于
"又一个刷装备游戏"和"又一个殖民地模拟"的唯一理由 ——
所以**任何设计取舍，优先保住这个闭环**。

## 0.3 核心循环（冻结）

```text
                    世界危机
                       ↓
        ┌──────────────┴──────────────┐
        │                             │
     家园系统                      副本系统
        │                             │
   发展居民 / 建设基地            单角色冒险
        │                             │
   生产资源 / 制作装备            击杀怪物 / 刷装备
        │                             │
   解锁科技 / 扩大领地            带回稀有资源
        │                             │
        └──────────→ 强化家园 ←───────┘
```

**为什么必须两条腿**：

- 只有家园 → "看 NPC 生活，但缺少长期目标"
- 只有刷图 → "又一个刷装备游戏"

**合起来**：白天管理自己的小村庄，晚上带一个角色出去冒险。**这是差异点。**

### 循环的节拍（冻结）

| 时段 | 玩家在做什么 | 系统在做什么 |
|---|---|---|
| 白天 | 建造 / 派工 / 看居民干活 | 居民按日程与需求自己运转 |
| 傍晚 | 挑一个居民，给他装备 | 居民数据 → 冒险者数据 |
| 夜晚（副本） | 单角色刷图 | 程序化房间 / 掉落 |
| 回来 | 把材料与装备放回家园 | 村庄变强 → 回到白天 |

> **关键约束**：**家园在玩家下副本时不能停止运转。**
> 这一条决定了未来联机与存档的架构（见 §0.4 的"世界归属"）。

#### 🔴 唯一红线：欠债 22 不能停

**欠债 22（居民到不了箱子）卡着生产链，也就是卡着「家园能自己转」。**
三条新 lane 各自独立，但**它们都靠"家园能自己转"才变成一个有意义的故事**。
家园那条停了，最后就是三个半成品 + 一个跑不起来的循环 ——
这正是 §82 说的「**系统依赖蔓延**」，而不是「代码写不出来」。

**并行的前提是文件不相交。** 一条 lane 顺手去改另一条 lane 的文件，就不是并行，是冲突。

> **建筑暂缓的直接理由**：Tiny Glade 式结构生成的工作量在**验证与手感**上，
> 而不在代码上。**一栋固定的房子足够支撑地形/农业/昼夜/光影/副本的全部验证**，
> 等这些跑通了再回头补建造，不会返工。
>
> 现有的轮廓绘制能力**保留不动**，它将来是模板系统的底层。

### ① 家园形态：一个主基地不断扩张 ｜ 多个村庄

**建议 A：一个固定主基地不断扩张。**
理由不是偏好，是三条既有约束：
`CozyTerrainSystem` 有**一个**固定原点、存档是**一个** `world.json`、
导航与房间图是**一张**图。B 需要世界切换，会同时动到地形/存档/导航三处。
而且 Willow 描述的联机模型（"一个玩家拥有自己的世界，别人来参观"）本身就是 A。

### ② 副本角色：自建英雄 ｜ 从居民里挑一个

**建议 B：从家园居民里挑一个。**
这正是 §0.1 那个亮点的实现方式，也是本项目唯一的差异点。
代价具体、可控：居民需要**装备栏**与**持久化**（现有 `CozyNpcState` 只有 job/skills/traits）。
选 A 的话，"培养铁匠"这条线就不成立了。

### ③ 战斗视角：俯视 ARPG ｜ 回合制 ｜ 动作

**建议 A：俯视 ARPG。**
同样不是偏好，是**沉没成本的方向**：真实 3D 空间 + 碰撞 + 导航网格 + 固定相机 +
像素精灵，**已经全部建好并且有断言护着** —— 这套东西正好就是俯视 ARPG 需要的。

- **B 回合制** 会把整套空间/导航/物理栈浪费掉（那是已经花掉的最贵的部分）
- **C 动作** 需要取消帧、判定盒、无敌帧、翻滚，**动画量翻数倍**，
  且固定相机下的 3D 动作手感很难调

⚠️ **但这一条会动到相机**：现有 pitch 40 是**建房子**的角度，
战斗需要能看清怪物、弹道与预警圈。**战斗场景的 pitch 很可能要加大**，
而 camera lock 的理由（E.1.1：一个观察方向 = 资产成本不翻倍）**必须继续遵守**。

### ④ 世界观：魔域入侵是否保留

**建议保留，但只作为背景前提，不做剧本。**
它的价值是**功能性**的：给"副本为什么存在"和"家园为什么要防御"一个统一解释，
让两半是**一个**循环而不是两个。删掉它，两半就得各自编理由。
成本：现在只写一段设定，不写任务、不写对话。

# 1. 锁定技术决策

## 1.1 坐标系

文档设计语义使用：

```text
X = 横向
Y = 平面前后
Z = 高度
```

但 Godot 使用 **Y-up**。当前项目锁定映射：

```text
doc(x, y, z) -> Godot(x, z, y)
```

因此：

```text
Doc Floor 0 = Z 0
Doc Floor 1 = Z 3

Godot Floor 0 = Y 0
Godot Floor 1 = Y 3
```

高度永远是真实空间高度，不是 Render Layer。

---

## 1.2 渲染方向

锁定：

> **Real 3D World + Perspective Camera (narrow FOV) + 2D Pixel Characters + Pixel-art Surface + Stylized Lighting**

当前约束：

| 层 | 决策 |
|---|---|
| 世界位置 | 真 3D |
| 楼层 | 真 3D 高度 |
| 墙 / 楼板 | 真 3D Mesh + Collider |
| 光照 | 真 3D |
| 摄像机 | **透视，窄 FOV（8–40°，由缩放档位推导）** |
| **相机角度** | **yaw 180 / pitch 40，锁定**（`L` 解锁仅供调试） |
| 角色 | 2D Pixel Sprite / Billboard（`AnimatedSprite3D`） |
| 表面 | Pixel-art Texture / Nearest |
| 输出基准 | 1280×720，`canvas_items` 拉伸 |

核心思想：

> **用 3D 解决空间问题，用 Pixel Art 解决视觉问题。**

### 2026-09-12 的两处变更

**投影从正交改为窄 FOV 透视。** 正交的理由（每个像素资产只做一个观察方向）
依然成立，窄 FOV 把这个破坏压到最小：默认缩放下画面只有约 17°，
一个站立角色跨过的密度变化不到一个像素。

**yaw 从 0 改为 180。** 这是**测量结果不是口味**：门切在 `z = 0` 那面墙上，
所以房子的正面朝 `-Z`；yaw 0 把相机放在 `+Z`（背面），
**开场永远隔着整栋房子**。yaw 180 下开场镜头 `0 opaque / 0 faded`。
`ground_forward()` 从 yaw 推导，**所以操作手感没有变**。

### 四类资产，四个生产者（Hybrid Pixel Diorama）

| 层 | 生产者 | 运行时形态 |
|---|---|---|
| 建筑 / 家具 | 程序化 / 手工 3D | 真 3D 几何 |
| **大树** | Blender 多层同心壳 | **2.5D 伪 3D mesh** |
| 草 / 花 / 小石 | AI 精灵 | Quad + billboard |
| **角色 / NPC** | **Blender 角色工厂（离线）** | **精灵表** |

> **Blender 是工厂不是运行时依赖。** 运行时角色仍然是 billboard 上的 PNG，
> 本节"角色 = 2D Pixel Sprite"**没有被推翻**。详见 `docs/ART_PROFILE.md` §9。

# 5. TerrainChunk 与多尺度 Terrain

世界必须切分 Chunk：

```text

├── Chunk_0_0

└── ...
```

Chunk 是：

- 内存管理单位。

- Dirty Region 的边界。
- 保存 / 加载单位。
- Terrain Mesh 重建单位。

## 5.2 FineGrid

FineGrid 不是屏幕像素，也不是建筑 Grid Snap。

它只是 Terrain 内部的离散计算单位。

玩家看到的是连续空间：


```text

Cell[1]
Cell[2]
...
```

因此两者可以共存：

```text
Continuous World
        │
        ▼
Terrain Rasterization
        │
        ▼
FineGrid
```

# 34. 材料消耗：建筑不再“凭空生成”

这是 V2.1 新增的正式规则。



```text

Wood = 30
```

# 58. Art Pipeline：无冕之乡统一生成式美术体系

## 58.1 重要说明：当前“无冕之乡”并没有锁死最终美术资产生产方式

当前 V2 工程中的 Art Policy 明确规定：

- 美术暂时使用 placeholder；
- 纹理由运行时程序生成；
- 真实 Pixel Art 素材未来接入时，原则上只需要替换 `render/pixel_art.gd` 与 `data/materials.gd`，不应修改核心游戏逻辑。

因此本章的目标不是声称“当前已经有一套最终美术资源”，而是为 **无冕之乡** 建立一套可以从现在开始执行、并且不会破坏 V2 架构的最终 Art Pipeline。

> **原则：美术资源可以为空，系统不能依赖资源本身才能运行。**

---

## 58.2 我们真正要模仿的不是某一张图，而是一套“视觉生成方式”

本项目希望获得的效果不是：

```text
每一个草
每一块石头
每一栋房子
每一个特效
都人工做一个最终模型
```

而是：

```text
少量高质量基础资产
        ↓
统一材质 / 色板 / 比例 / 细节规则
        ↓
程序化组合
        ↓
程序化变体
        ↓
环境散布
        ↓
最终统一画面
```

因此我们的目标是建立：

> **Base Assets + Procedural Assembly + Procedural Distribution + Procedural VFX + Shared Art Grammar**

这与本项目当前“真实 3D 空间 + Orthographic Camera + Pixel Art Surface”的总路线是一致的。

---

## 58.3 五层美术架构

所有游戏美术分为五层：

```text

    ↓

    ↓
Layer 3  Procedural Assembly
    ↓
Layer 4  Procedural Distribution / VFX
    ↓

```

### Layer 1：Art Grammar

定义整个游戏“长什么样”。

```text

Edge Language
Material Language
Detail Scale

VFX Language
```

### Layer 2：Base Assets

例如：

```text

Flower_A

Pebble_A
TreeTrunk_A
LeafCluster_A
StoneBlock_A
WoodPlank_A
RoofTile_A

```

### Layer 3：Procedural Assembly

把原子资产组合成：

```text
Ground
Bush
Wall
Roof
House
Road
Bridge
Tree
Garden
```

### Layer 4：Procedural Distribution / VFX

决定它们：

```text

怎么变化
怎么运动
怎么响应环境
```

### Layer 5：Renderer

统一做：

```text

Nearest Sampling
Depth

VFX Composite
```

## 58.4 地面植物不要制作成“每一根草的模型”

这是整个地表美术系统最关键的原则之一。

不建议：

```text

Grass_0003.glb

```

```text

LeafCluster
TinyFern

```

然后由 `VegetationScatterSystem` 负责组合。

```text

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓
```

# 75. 已经暴露过的 Bug 与必须保留的修复规则

不能把“走得久”直接当作“被卡住”。

```text
Agent not moving
```

## 74.2 Ramp Collider

坡道必须从低端进入，且顶部必须有 Landing。

## 74.3 Floor Collision

楼板是真正的 Collider，不能只是渲染表面。

---

## 74.4 Arrival Check

走完 waypoint != 到达。

最终：

```text
distance(actual_position, target)
```

必须满足阈值。

## 74.5 Stairwell 两层处理

楼梯口可能在：

- 下层为实体斜坡。
- 上层为楼梯孔。

两个楼层都必须进行正确的障碍判定。

## 74.6 InteractionPoint World Transform

InteractionPoint 在 Planning 时必须已经是正确 World Position，不能等待 `_process` 才更新。

## 74.7 T-Junction

必须进行 Planar Subdivision。

# Appendix E：V2 美术资产与渲染管线（Fixed Camera Pixel World）

> 本章正式锁定 V2 的美术生产方式。
>
> **固定相机角度 + 真实 3D 建筑 + 像素化非建筑资产 + 像素 VFX + 统一色板/灯光。**
>
> 本章中的“无冕之乡式”仅表示目标视觉方向的参考，不声称复刻其内部源码或完整技术管线。公开开发资料可以支持其使用 Godot、WorldEnvironment、灯光/阴影与像素化相关 Shader 的方向，但无法据此断言其全部资产生产方式。

## E.1 美术总原则

### E.1.1 固定机位

相机采用固定或严格受控的 Orthographic Camera：

```text
Camera
├── Position：锁定
├── Rotation：锁定
├── Orthographic：true
├── Zoom：有限档位
└── Pixel Framing：锁定
```

第一版禁止让玩家自由旋转相机作为核心玩法要求。

原因：固定机位可以让我们为一个确定的观察方向制作像素资产，从而显著降低植物、NPC、VFX 和环境装饰的生产成本，同时提高 AI 生成资产的一致性。

### E.1.2 “3D”与“Pixel Art”不是二选一

```text
真实 3D
    ↓
负责：
位置 / 楼层 / 碰撞 / 导航 / 建筑结构 / Terrain 高度

Pixel Art
    ↓
负责：
人物 / 植物 / 小物件 / VFX / 材质细节 / 色彩语言
```

因此：

> **3D 是空间标准，不是所有美术资产必须使用 3D 模型。**

### E.1.3 建筑是主要的 3D 资产类别

建筑必须继续使用真实 3D Geometry，因为它需要：

```text
Wall
Floor
Roof
Door
Window
Stair
Foundation
Column
Beam
Collision
Room
Navigation
```

建筑视觉：

```text
3D Geometry
    +
Pixel-oriented Material
    +
Stylized Lighting
    +
Procedural Detail
```

### E.1.4 建筑之外默认优先 Pixel Asset

除少量必须 3D 化的特殊世界对象外，以下默认采用 Pixel Sprite / Billboard / Card：

```text
Grass
Flowers
Fern
Bush
Leaves
Small Tree Canopy
Small Rocks
Pebbles
Mushrooms
NPC
Animals
Fire
Smoke
Dust
Magic Particles
Leaves
Rain
Snow
Small Decorations
```

# E.6 像素规格标准

由于本项目固定机位，像素密度必须锁定。

建议第一版建立三个规格：

```text
Small   = 16~32 px 高
Medium  = 32~64 px 高
Large   = 64~128 px 高
```

例如：

```text
小草       16~24px
花         16~24px
小石头     16~24px
灌木       32~48px
NPC        48~96px
小动物     32~64px
树         64~128px
大型特殊树  128px+
```

实际数值由游戏最终 Camera Zoom 和截图测试锁定；以上是资产生产初始规范，不是硬编码。

### E.6.1 统一像素密度

最重要的不是“全部 32×32”，而是：

> **在最终固定 Camera 下，同一世界里的物体具有相近的视觉像素密度。**

# E.20 Procedural Scatter 规则

Scatter 不是纯随机，而是：

```text
Terrain Material
+
Biome
+
Slope
+
Moisture
+
Fertility
+
Distance to Road
+
Distance to Building
+
Seed
```

### E.20.1 基本公式概念

```text
SpawnProbability
=
BaseDensity
× BiomeMultiplier
× TerrainMultiplier
× SlopeMultiplier
× DistanceMultiplier
× Random(seed)
```

### E.20.2 建筑边缘



# E.27 为什么不要把整个人物画成一张图再直接骨骼变形

因为像素艺术与连续网格形变存在天然冲突。

如果整个人物：

```text
一个 Sprite
    ↓
Smooth Bone Deformation
```

很容易出现：

```text
像素被拉长
像素被压扁
轮廓出现奇怪锯齿
关节变糊
衣服穿模
```

因此本项目 NPC 默认使用：

> **Rigid Cutout 2D Bone Animation**

而不是大范围 Smooth Mesh Deformation。

# E.29 Godot 2D Skeleton 方案

Godot 原生提供：

```text
Skeleton2D
Bone2D
```

并可以将 2D 多边形绑定到骨骼，使用权重进行变形。官方文档也提供了完整的 Skeleton2D / Bone2D 设置和权重流程。citeturn699087search0turn699087search2

但是我们的像素人物默认不要大量使用权重变形。

建议：

```text
Bone2D
  ↓
Sprite2D 部件
```

例如：

```text
upper_arm_L.png
forearm_L.png
hand_L.png
```

分别挂到：

```text
upper_arm_L Bone
forearm_L Bone
hand_L Bone
```

这样旋转时：

```text
像素图整体旋转
```

不会把图像拉成一团。

# E.36 NPC Animation 与 Gameplay 解耦

NPC 不直接说：

```text
play_animation("research_table_animation")
```

而是：

```text
NPC State = WORKING
WorkType = RESEARCH
```

Animation Controller 根据：

```text
NPC State
+
Action
+
Direction
+
Equipment
```

选择：

```text
Animation Clip
```

例如：

```text
WORKING + RESEARCH
→ work_research_side

WORKING + TEXTILE
→ work_textile_side

SLEEPING
→ sleep_side
```

# E.37 NPC 与 InteractionPoint

NPC 不直接知道家具模型。

它只知道：

```text
InteractionPoint.type = WORK
InteractionPoint.action = RESEARCH
```

执行后：

```text
NPC
 ↓
Walk
 ↓
AlignToInteractionPoint
 ↓
FaceTarget
 ↓
Play Action Animation
 ↓
Wait Duration
 ↓
Apply Result
```

这样同一套 NPC Animation Controller 就可以支持：

```text
研究桌
纺织机
工作台
炼金台
厨房
魔法台
铁匠炉
```

# E.40 固定机位下 NPC 的“假三维”策略

NPC 虽然是 2D Pixel Sprite，但逻辑位置永远是 3D：

```text
NPC.position = Vector3
```

Renderer：

```text
3D Position
    ↓
Camera Projection
    ↓
Sprite Screen Position
```

这样 NPC 可以真正：

```text
站在地面
站在二楼
站在桥上
站在楼梯
站在房间后面
```

但是视觉仍然是一张像素人物。

# E.41 NPC 骨骼方案选择

## 方案 A：Godot Skeleton2D

**推荐作为第一版。**

优点：

```text
免费

与 Godot 集成
不用额外运行时
适合我们的项目规模
```

官方文档明确支持 Skeleton2D、Bone2D 和 2D 骨骼变形。citeturn699087search0turn699087search2

## 方案 B：Spine

当 NPC 系统变复杂时再考虑：

```text
大量角色
大量换装
复杂 IK
复杂动画状态
大量可复用动画
```

第一阶段不强制引入 Spine。

## 方案 C：纯逐帧

适合：

```text

重要 NPC
Boss

```

不适合：

```text

```

最终推荐：

> **普通 NPC = Bone Rig + 少量 Pixel Corrective Frames；主角/重要 NPC = Hybrid / Frame-by-frame。**

# E.42 NPC “绑定骨骼”具体操作规范

### Step 1：先做 Rest Pose

```text
双脚自然站立
双臂略微打开
头正面
躯干直立
```

### Step 2：拆 Sprite

```text
head.png
torso.png
upper_arm_L.png
forearm_L.png
hand_L.png
upper_arm_R.png
forearm_R.png
hand_R.png
thigh_L.png
shin_L.png
foot_L.png
thigh_R.png
shin_R.png
foot_R.png
```

### Step 3：建立 Skeleton2D

```text
root
→ pelvis
→ spine
→ chest
→ neck
→ head
```

### Step 4：建立四肢 Bone2D

```text
chest
├── shoulder_L → upper_arm_L → forearm_L → hand_L
├── shoulder_R → upper_arm_R → forearm_R → hand_R
├── pelvis → thigh_L → shin_L → foot_L
└── pelvis → thigh_R → shin_R → foot_R
```

### Step 5：Sprite 跟随骨骼

每个 Sprite 作为对应 Bone2D 的子节点，优先进行刚性旋转，不做大面积网格拉伸。

### Step 6：建立动画

```text
idle
walk
work
sit
sleep
interact
```

### Step 7：像素修正

对：

```text
手
脚
脸
头发
衣服边缘
武器
```

进行关键帧像素修正。

# E.43 为什么不建议“AI 直接生成完整动画 Sprite Sheet”作为唯一方案

AI 很容易产生：

```text
脸变
衣服变
武器变
身材变
像素密度变
```

因此 AI 动画应该作为：

```text
参考
原型
动作草图
```

而不是直接成为长期的唯一 Animation Source。

更稳定的方式：

```text
AI Character Sheet
        ↓
固定角色模板
        ↓
Rig
        ↓
动画
        ↓
Pixel Correction
```

# E.44 NPC 批量生成策略

不要每个 NPC 从零开始。

建立：

```text

EquipmentSet
```

然后 Definition：

```json
{
  "id": "villager_worker",
  "body": "body_medium_01",
  "hair": ["hair_01", "hair_02", "hair_05"],
  "clothing": ["shirt_01", "shirt_03", "apron_02"],
  "palette": "village_warm",
  "allowed_jobs": ["farmer", "builder", "worker"]
}
```

NPC Instance 只保存：

```text
body_id
hair_id
face_id
clothing_id
palette_id
```

这样存档很小，也容易批量生成。
