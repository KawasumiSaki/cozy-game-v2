## ① Entity：薄注册表，不是 ECS

### 实测现状

- `CozyNpcState`（居民数据）、`CozyCharacter`（身体/精灵）、`CozyAppearanceDefs`（外观）
- `CozyWorldObject`（家具）、`CozyWall` / `CozySlab` / `CozyRoof`（视图）
- **每个系统自己管自己的 id**：`wall_001`、`npc_001`、门是 `wall_001_door`
- **没有一处能回答"给我 id 为 X 的实体"**

已有的、值得保住的形状：**State 是事实，View 是派生的**（doc §18/§32）。
`_sync_views` 按 id 对账、局部重建——这条已经是正确架构。

### 要冻结什么

```
Entity = id + 一组具名 State 对象
```

一个薄注册表 `CozyWorld`：

| 方法 | 作用 |
|---|---|
| `register(id, state)` / `unregister(id)` | 生命周期 |
| `state_of(id)` | 唯一的解析入口 |
| `all_of(kind)` | 存档、UI、批量操作用 |

**落地形态**（2026-09-12 实测后补）：

| 提案 | 落地 | 为什么 |
|---|---|---|
| `register(id, state)` | `register_kind(kind, provider, encode)` | **kind 是拉取的 Callable，不是推一次**。收一次就过期——本项目已为这个形状付过两次（bug 18 / 19） |
| — | 每 kind 可选 `encode` | **没 encode 的 kind 永不进存档**——屋顶就这样排除。排除写在注册处而不是存档处，**将来新增派生 kind 不会因为忘了跳过而被存进档** |
| `unregister(id)` | 由拥有者从自己的列表里删 | 注册表不持有实体，只持有"怎么枚举" |
| `state_of(id)` | `state_of(id, kind := "")` | id 撞车时**拒绝解析**（返回 null），`kind` 是消歧义的后门；`duplicate_ids()` 是探测器 |
| `all_of(kind)` | `all_of(kind)` | 另加 `persisted_entities()` / `payloads(doc, kind)`（读档） |

**编码器有，解码器没有**，这个不对称是故意的：注册表能**索引**任何 state，
但一个解出来的墙必须由**拥有那个列表的人**追加进 `building.state.walls`。
编码是"描述你有的"，解码是"把它装回去"，只有拥有者做得了第二件事。

**存档因此变成一条实体列表**（这是提案里写的收益，真的落地了）：
v1 的 `building` / `objects` / `npcs` 三个顶层键合成 `entities: [{kind, state}]`。
地形与 id 计数器**不是实体**，各留一个键（一个是场地、一个没有被寻址的 id）。
家具在 v1 里**根本没有 id**（靠数组下标认身份），迁移步骤给它补发。

**不是 ECS。** 没有系统遍历组件、没有 archetype、没有每帧查询。理由是**不需要**：
本项目的实体数量在数百级，瓶颈从来不是遍历，而是"改一处要通知谁"——
那个问题由 ⑤ 回答。

### 明确不做

```text
❌ Component 基类 / 组件数组
❌ 每帧 System 遍历
❌ 为了 ECS 重写 CozyNpcState / CozyWorldObject
```

**但要留一条口子**：`CozyNpcState` + `appearance` 五槽 + 工种/技能/特质/日程
**在实践中已经就是组件式的**——加一个新工种是一行数据。将来"怪物"要有
`CombatComponent`，那时再加，**不是现在**。

### 为什么这个冻结现在重要

两点都会**立刻**受益，且都不需要新玩法：

1. **存档**：现在 `to_dict()` 是各系统拼出来的顶层键。有了注册表，实体是**一张列表**。
2. **副本里的英雄**：Willow 已定 **2B（从居民里挑一个去冒险）**。
   "同一个实体，在家园是一种用法，在副本是另一种"——**这正是注册表要解决的问题**。

## ② Data 格式：冻结为 GDScript const

### 实测现状

9 张表，全部是 `data/*.gd` 里的 `const`：

```
appearance  buildings  jobs  materials  objects  recipes  schedule  skills  traits
```

**反模式检查结果：全项目没有一处 `if type == "farmer"` 这类分支。**
数据驱动**已经做到了**，不是待办。

### 要冻结什么

> **数据表留在 `data/*.gd`，写成 `const`，直到出现一个能被说出名字的理由。**

理由（为什么 GDScript const 优于 JSON，**在这里**）：

| | GDScript const | JSON |
|---|---|---|
| 类型 | 编译期检查 | 运行期才发现 |
| 错误时机 | **解析失败，立刻** | 启动后静默回落 |
| 导出构建 | 直接可用 | 要处理路径与清单 |
| 重构 | 改名会一起改 | 字符串，改了不知道 |

本项目的**已经吃过**这两类亏：
`CozyAssetLibrary` 拒绝畸形定义**并给原因**（因为无法信任数据），
`from_name()` 未知回落到 NATURAL（**静默**，已记录）。
JSON 会把这两类问题从"编译期"推到"运行期"。

### 明确不做

```text
❌ 现在把 data/*.gd 改成 JSON
❌ 建一个通用 "DataLoader"
❌ 允许数据里出现脚本/表达式
```

### 出现什么理由时才翻案

**说出名字**才行，例如：要做 mod 支持、要热重载、要让非程序员编辑。
**"JSON 比较标准"不是理由。**

## ③ Resource 加载：契约冻结，机制必须换

### 实测现状

- 契约已经是好的：`load_dir(path)` 收路径 → 逐份校验 → **RAW 绝不进运行时**（代码强制）
- **但枚举方式是 `DirAccess` 扫目录** —— 编辑器与 headless 可用，**导出构建不行**

这是**已知欠债 4**，而且它是**唯一一条会真的挡住发布**的。

### 要冻结什么

**契约冻结**（不动）：

```
path in -> definitions out -> invalid ones refused WITH A REASON -> runtime gets APPROVED only
```

**机制必须换**（在第一次导出构建之前）：

| 方案 | 代价 | 备注 |
|---|---|---|
| 生成一份 manifest JSON | 需要一个构建步骤 | 最小改动 |
| Godot `.tres` 资源 | 要把 JSON 转过去 | 引擎原生 |
| 定义改用 `preload()` | 失去"扫目录"的灵活性 | 最稳 |

**冻结一个判据而不是一个方案**：
> **导出构建里必须能列出全部资产，且不依赖文件系统枚举。**

### 明确不做

```text
❌ 现在换（V0.1 没有导出计划）
```

**但要写进"发布前必做"清单** —— 它是唯一一条"不换就发不出去"的。

## ④ Save：定迁移政策

### 实测现状

**比我以为的好**：`CozySaveManager` **已经有** `const VERSION := 1`，
而且**拒绝**读版本不对的档，而不是硬读一半（注释原话：
"refusing rather than half-reading it"）。

缺的是：

- **只有一个槽**（欠债 20）
- **没有迁移政策**：现在版本对不上就是拒读。V0.1 阶段这是**对的**，
  但一旦有玩家，拒读 = 丢档

### 要冻结什么

```
① 版本号语义：什么时候 +1
     加字段                 -> 不 +1（向后兼容，旧档能读）
     改字段语义 / 删字段     -> +1
② 每个版本配一个 migrate(from, to)
③ 迁移失败 = 拒读 + 明确原因（保持现在的行为，但要有原因）
④ 迁移必须可测：用 tests/fixtures/ 里的旧档跑
```

**关键**：`tests/fixtures/` 现在只放美术夹具。
**旧版存档夹具**应该放进去 —— 那是迁移唯一可靠的验证方式，
而且它让"迁移"从一句承诺变成一个断言。

### 明确不做

```text
❌ 现在加多槽（欠债 20，等 UI 一起做）
❌ 现在写 migrate（VERSION 还是 1，没有 from 可以迁）
```

**现在只做一件事**：把**政策**写下来，并**加一个旧档夹具目录**。

## ⑤ Event：**不做事件总线**

### 实测现状

**没有事件系统**，全是直接调用。但看看实际是什么样：

```
_rebuild_spatial(dirty)       <- 收一个脏区域
   ↓ 只重算受影响的楼层（墙在一层，改不了另一层的房间，doc §33）
   ↓ 房间 -> Portal -> RoomGraph -> 导航
_build_roofs()
_refresh_scatter()
```

**这就是总纲 §32 的脏依赖图，而且已经实现了。**
`CozyDirtyRegion`、`dirty_chunks()`、局部重建 —— 都在跑，且有断言。

### 要冻结什么

> **不要事件总线。脏依赖图就是这一层的答案。**

理由：

- 总线把**顺序**变成隐式的。而现在顺序是**显式**写在调用点上的，
  并且**可断言**（"改一面墙只脏 1 个 chunk"、"屋顶跟着房间走"就是这么测的）。
- 总线让"谁依赖谁"无法静态阅读。本项目**已经为隐式依赖付过代价**——
  散布与地形渲染器抢脏区集合（欠债 6），根因就是**顺序不明确**。
- 事件总线最常见的用途是**解耦**。本项目需要的是**顺序**，两者不是一回事。

### 明确不做

```text
❌ EventBus / SignalHub autoload
❌ 用信号取代 _rebuild_spatial 的显式顺序
```

### 但要补一件事

`_rebuild_spatial()` 现在**住在 `main.gd` 里**，而它描述的是**系统之间的依赖顺序**——
那是架构，不是场景接线。**它应该有一个独立的名字和位置**
（和 ⑤ 的"不做总线"不冲突：这是**收拢**，不是解耦）。
