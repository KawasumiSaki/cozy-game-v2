
## —— Pixel Art × 真实三维空间 × 自由建筑 × 可编辑地形 × NPC 模拟

> **版本：V2.0**  
> **引擎：Godot 4.x**  
> **目标平台：PC + Mobile**  
> **游戏类型：单人生活 / 冒险 / 建造 / 模拟 RPG，少量可选多人合作**

---
第一段
# 1. 项目定位

本项目是一款**原创的 Pixel Art 风格生活冒险模拟 RPG**。

游戏的核心不是简单地：

> “玩家 → 点击按钮 → 建一个房子 → NPC 自动生产。”

而是希望建立一个真正具有**空间、结构、物体和生命活动**的世界。

玩家可以：

- 改变土地；
    
- 挖掘、填平、铺路；
    
- 自由建造房屋；
    
- 建造多层建筑；
    
- 自由摆放家具；
    
- 移动、旋转、重新布置物品；
    
- 进入房屋内部；
    
- 使用各种设施；
    
- 招募 NPC；
    
- 给 NPC 分配工作；
    
- 让 NPC 自主取材料；
    
- 让 NPC 走到机器前工作；
    
- 让 NPC 上下楼；
    
- 让 NPC 回家、睡觉、休息；
    
- 逐渐建立自己的村庄和生活空间。
    

最终希望形成一种感觉：

> **玩家不是在编辑一张地图，而是在创造一个真正可以生活的世界。**

# 3. 核心设计理念

整个项目最重要的不是某一个具体系统，而是下面这句话：

> **土地是细粒度的，建筑是模块化的，物品是自由放置的，空间是真实三维的，互动是真实发生的，NPC 是自主生活的，而最终视觉是一幅可以活动的像素画。**

可以拆成六层。

例如：

```text

在 Floor 1

在另一个 Floor 1

墙体

```

仅靠：

```text

```

无法准确判断真正的空间关系。

> 用 3D 解决“空间问题”，用 Pixel Art 解决“视觉问题”。

# 7. 系统之间的核心关系

整个游戏最底层的依赖关系：

```text

      ↓

      ↓
Collision
      ↓
Navigation
      ↓
NPC
      ↓
Interaction
      ↓

```

Renderer 则贯穿所有系统：

```text
Spatial
Building
Terrain
Object

        ↓
    Renderer
        ↓
     Pixel Art
```

换句话说：

**SpatialSystem 决定“它在哪里”。**

**BuildingSystem 决定“这里是什么结构”。**

**TerrainSystem 决定“这里是什么土地”。**

**ObjectSystem 决定“这里有什么东西”。**

**InteractionSystem 决定“东西能做什么”。**

**NPCSystem 决定“谁来做”。**

**Renderer 决定“玩家看到什么”。**

# 8. SpatialSystem

SpatialSystem 是整个游戏最重要的底层系统之一。

它不负责：

> “这个东西好不好看。”

它只负责：

> **“这个东西到底在哪里？”**

---

# 8.1 世界坐标

所有实体都拥有：

```text
position
rotation
scale
```

例如：

```text
Player
position = (12.4, 8.7, 0.0)

Chair
position = (13.2, 8.1, 0.0)

ResearchTable
position = (16.5, 9.2, 0.0)

TextileMachine
position = (16.5, 9.2, 3.0)
```

其中：

```text
X = 左右
Y = 前后
Z = 高度
```

---

# 8.2 Floor

Floor 是真正的空间层级。

例如：

```text
Floor 0
Z = 0

Floor 1
Z = 3

Floor 2
Z = 6
```

地下室：

```text
Basement
Z = -3
```

阁楼：

```text
Attic
Z = 6
```

实际的楼层高度应该成为建筑系统的参数，而不是在所有代码里写死。

---

# 8.3 Room

房间是空间中的一个区域。

每个 Room：

```text
Room
├── id
├── floor
├── polygon
├── doors
├── objects
└── navigation_area
```

例如：

```text
House
│
├── Floor 0
│   ├── Laboratory
│   └── Storage
│
└── Floor 1
    ├── TextileRoom
    └── Bedroom
```

---

# 8.4 为什么要有 Room

因为 NPC 不应该只理解：

> “我要从坐标 A 去坐标 B。”

它还应该理解：

> “我要从实验室去二楼的纺织室。”

因此：

```text
Laboratory
↓
Door
↓
Hall
↓
Stair
↓
Floor 1
↓
TextileRoom
```

这就形成了一个：

> **Room Graph**

---

Portal 是空间之间的连接器。

例如：

```text

Tunnel
Cave Entrance
```

都可以被抽象成：

```text
Portal
```

例如：

```text

   ↓
 Door
   ↓
Room B
```

或者：

```text

   ↓
 Stair
   ↓
Floor 1
```

# 10. Renderer

Renderer 负责把：

```text
真实空间
```

变成：

```text
玩家看到的画面
```

---

# 10.1 Orthographic Camera

推荐：

> Orthographic Camera

而不是普通透视 Camera。

主要原因：

### 1. Pixel Art 更容易控制

远近不会导致：

```text
像素大小发生巨大变化
```

### 2. 更接近经典斜视 RPG

### 3. 建筑更容易保持统一比例

### 4. 多楼层更容易控制

### 5. 可以保留类似手绘地图的感觉

---

# 10.2 视觉结构

最终：

```text
World
↓
3D Geometry
↓
Pixel Materials
↓
Pixel Character
↓
Stylized Lighting
↓
Post Processing
↓
Pixel Art
```

---

# 10.3 Character

角色建议：

```text
3D Position
+
2D Pixel Sprite / Billboard
```

也就是说：

角色实际上存在于：

```text
X
Y
Z
```

但玩家看到：

```text
Pixel Sprite
```

例如：

```text
NPC.position
=
(12.4, 7.8, 3.0)
```

代表 NPC 在：

```text

```

但是 Renderer 最终绘制：

```text

```

---

# 10.4 为什么这个方案非常适合项目

它同时解决：

```text
3D
↓
空间
碰撞
楼层
遮挡
导航
```

以及：

```text

↓
像素视觉
角色美术

```

因此：

> **空间和美术不再互相绑死。**

# 11. Depth

V2 不应该依赖传统的：

```text

```

因为：

```text

Floor 1
Floor 2
```

之间存在真实高度。

```text

+
```

# 12. Occlusion

建筑会挡住玩家。

例如：

```text
Camera
   ↓
  Wall
   ↓
 Player
```

如果直接渲染：

```text
玩家消失
```

所以必须存在：

> Occlusion System

---

# 12.1 玩家进入房屋

玩家进入：

```text
Room A
```

系统知道：

```text
Player.floor
Player.room
Player.position
```

然后判断：

```text
哪些墙遮挡玩家？
哪些屋顶遮挡玩家？
哪些房间应该显示？
哪些房间应该隐藏？
```

---

# 12.2 Interior Fade

推荐：

```text
Roof Fade
Wall Fade
Room Reveal
```

而不是：

```text
整栋房子直接消失
```

例如：

```text
玩家进入房间
        ↓
检测遮挡玩家的 Wall
        ↓
Wall Fade
        ↓
屋顶 Fade
        ↓
玩家所在 Room Reveal
```

这样既能看到玩家：

又不会失去建筑结构。

# 15. BuildingSystem

BuildingSystem 是整个游戏的**自由建造核心**。

它需要解决的问题不是：

> “玩家选择一个房子 Prefab，然后放到地上。”

而是：

> **玩家给出建筑意图，系统根据建筑结构自动生成房子。**

也就是说：

```text
玩家操作
   ↓
建筑意图
   ↓
BuildingSystem
   ↓
结构解析
   ↓
程序化生成
   ↓
墙 / 地板 / 屋顶 / 门 / 窗 / 楼梯
   ↓
真实 3D 建筑
```

---

# 16. 为什么不能使用传统 Tile Building

传统 Tile 建筑：

```text
□ □ □ □
□ □ □ □
□ □ □ □
```

玩家只能：

```text
放一个墙 Tile
放一个墙 Tile
放一个墙 Tile
```

这样很容易出现：

```text
房屋像棋盘
房屋像拼图
建筑尺寸被 Tile 限制
斜墙很难处理
屋顶很难自然连接
```

而本项目希望：

```text
       ╱──────────╲
      ╱            ╲
     │              │
     │              │
     │              │
     └──────────────┘
```

甚至：

```text
      ╱──────╲
     ╱        ╲
    │          ├───────╮
    │          │       │
    │          │       │
    └──────────┴───────┘
```

所以建筑系统必须支持：

- 任意长度；
    
- 任意角度；
    
- 不同高度；
    
- 墙体连接；
    
- 墙体分叉；
    
- 房间合并；
    
- 房间拆分；
    
- 屋顶自动生成。

# 19. Wall System

Wall 是建筑系统最基础的组件。

一个 Wall 不应该表示：

```text
一个 Tile
```

而应该表示：

```text
一条线段 + 一组建筑参数
```

---

## 19.1 Wall 数据

```text
Wall
├── start
├── end
├── height
├── thickness
├── material
├── style
├── openings
└── connections
```

例如：

```text
start = (10, 10, 0)
end   = (20, 10, 0)

height = 3
thickness = 0.2

material = Wood
style = Plank
```

系统根据：

```text

+
end
+
height
+
thickness
```

自动生成 Wall Mesh。

---

# 20. Wall 可以任意长度

例如玩家拖动：

```text
A ───────────────── B
```

系统计算：

```text

```

然后自动：

```text
生成墙体
↓
计算纹理重复
↓
计算柱子
↓
计算连接点
```

因此：

```text
3m
5m
8m
13.7m
```

都可以。

---

# 21. Wall 可以旋转

玩家可以：

```text

45°
90°
135°
```

甚至：



# 44. 为什么 Terrain 要 Fine Grid

因为你希望实现：

```text
挖一小块
```

而不是：

```text
删除一整块 Tile。
```

例如：

```text
████████████
██████░░████
█████░░░░███
██████░░████
████████████
```

其中：

```text
█ = Grass
░ = Soil
```

这就可以形成自然的：

```text
坑
沟
道路
河岸
农田
```

---

# 45. Fine Grid 不等于 Pixel

非常重要。

不要理解为：

```text
屏幕每一个 Pixel
=
一个 Terrain Cell
```

而应该：

```text
Terrain Cell
↓
较细粒度的世界模拟单位
↓
Renderer
↓
Pixel Art
```

例如：

```text
1 Cell = 0.25m
```

或者：

```text
1 Cell = 0.1m
```

具体数值以后通过性能测试决定。

---
