## 目标

融合 RimWorld 家园模拟 · Tiny Glade 程序化建造 · Diablo/Chronicon 刷宝副本 · 数据驱动内容系统。

**核心原则：不要从零设计所有系统。** 参考成熟开源项目思想，但**不直接复制代码**。

## 一、整体架构参考

所有程序化生成系统统一采用：

```
输入：Seed + 规则 + 模板
   ↓
输出：World Data
   ↓
Renderer
```

例如地图：`{"type":"forest","seed":12345,"size":"50x50"}` → 生成 terrain / resources / objects。

> **与本项目的关系**：这条已经在跑。`CozyArtSeed`（确定性种子）+ `data/*.gd`（规则与模板）
> + Generator（`CozyScatterRule` / `CozyRoofGenerator` / `CozyOutlineGenerator`）
> 就是同一个形状，而且有断言护着「同一世界重建后一致」。

## 二、RimWorld 家园系统参考

**核心思想：不要让 NPC 直接执行行为。**

```
需求 → 任务(Job) → 执行(Action) → 结果
```

例：NPC 发现木材不足 → 生成 `Job{type:"cut_tree", target:"tree_001"}` → 移动 → 砍树 → 获得木材 → 返回仓库。

**第一版不要复杂人格**，只要 `Needs + Jobs + Skills`。

> **与本项目的关系**：**已经实现。**
> `CozySchedule`（活动→交互点）/ `CozyJobDefs`（工种→要找的点类型）/
> `CozyNpcState`（需求、技能、特质）/ `CozyNpcAgent`（FSM: IDLE/GOING/WORKING）。
> 反模式检查：**全项目没有一处 `if type == "farmer"`**。
> 缺的只有**采集类资源点**（树/矿/农田）—— 那是 V0.1 的待办，不是架构问题。

## 三、副本程序化生成系统

### 设计目标

**不是纯随机 Roguelike**，而是：

```
程序生成 → 人工编辑 → 固定副本模板 → 运行时轻随机
```

**开发阶段：**

```
Dungeon Generator → 生成初始地图 → 设计师调整
                                    ↓
                          保存为 Dungeon Blueprint
                                    ↓
                            游戏运行读取
```

**运行阶段：**

| 固定 | 随机 |
|---|---|
| 地图结构 | 怪物数量 |
| Boss 位置 | 精英怪 |
| 剧情事件 | 宝箱 · 掉落 · 事件 |

同一个副本，第一次是普通狼×5 + 普通装备，第二次是精英狼×2 + 稀有装备。

### 1. 开发阶段三步

- **Step 1 程序生成**：输入 Dungeon Type / Seed / Room Rules / Difficulty → 输出房间图
- **Step 2 人工编辑**：设计师改房间连接、地形、怪物点、宝箱、Boss 区、机关
- **Step 3 保存蓝图**：运行期读取

### 2. 副本结构

```
Dungeon → Room Graph → Room Template → Content Spawn
```

**Room Template 人工制作**，每个房间包含 Terrain / Spawn Point / Decoration / Loot Point / Enemy Point。

### 3. ⚠️ 蓝图存什么 —— **这里必须改**（Claude 修订 2026-09-12）

原文的蓝图长这样：

```json
{ "id": "forest_dungeon_01",
  "rooms": [ {"id":"room_001","type":"forest"}, {"id":"boss_room","type":"boss"} ] }
```

**这是在「编写房间」。而本项目的第一条不变量是**（`docs/INVARIANTS.md`）：

> ## Rooms are DERIVED, never authored
> 房间由墙图经**平面面遍历**推导（`CozyRoomDetector`）。**绝不手放一个房间。**

所以蓝图**存墙，不存房间**：

```json
{ "id": "forest_dungeon_01",
  "version": 1,
  "outlines": [ [0,0, 12,0, 12,8, 0,8], [14,0, 22,0, 22,10, 14,10] ],
  "links":    [ {"a":0, "b":1, "kind":"door"} ],
  "spawns":   [ {"room_hint":"entrance", "kind":"player"} ],
  "content":  [ {"room_hint":"elite", "table":"forest_elite", "count":[1,2]} ] }
```

**存墙比存房间更强，而且不是勉强够用：**

```
outlines → CozyOutlineGenerator.plan() → CozyBuildingIntent → CozyBuildingSystem
                                                                     ↓
                        房间 · Portal · RoomGraph · 导航 · 屋顶 · 遮挡淡出 · 存档
```

**全部已经有 118 条断言护着。地牢不需要一套平行系统 —— 它只是另一批墙。**

**而且存房间会骗人**：设计师改一面墙之后，房间数据就与几何不符了，
而「房间」在运行时是推导出来的、永远正确的那一份。两份数据必然漂移。

**`room_hint` 是提示不是事实**：内容生成要知道「哪个房间放精英」，
但**不能在蓝图里断言那个房间是哪个 id** —— 存的是几何上的哪个区域，
运行时由推导出来的房间去匹配。这样墙一动，提示仍然落在同一块地方。

**附带好处**：`Rooms are derived` 还白送 V2-16 的开口语义 ——
门是墙上的 `CozyOpening`，不是蓝图里的一条边，所以门洞左右仍是**同一个房间**
（这条也是不变量），通路则由墙推导出的 Portal 表达。

## 四、装备系统设计

**不是「生成装备」，而是组合：**

```
Base Item + Affix + Quality + Socket + Legendary Effect
```

```json
{ "id":"sword_001", "type":"sword", "damage":10, "quality":"rare",
  "affixes":["fire_damage","attack_speed"], "sockets":["ruby"] }
```

基础 Iron Sword + 火焰伤害 20% + 攻速 10% + 红宝石孔 → **Flaming Ruby Sword**。

> **与本项目的关系**：`data/materials.gd` 已经是**物品词汇表**（§35：不为建筑材料另建库存系统），
> 加一行就是一个新物品。词条需要一张新表 + 一个生成器 —— **纯函数，正好进 `tests/unit/`**。

## 五、建筑系统设计

**不采用完全自由建造**，采用 `建筑模板 → 参数调整 → 自动生成`。
选 Small Cottage，调 width / length / height / material / roof / decoration → 生成墙、门、窗、屋顶、家具。

> **与本项目的关系**：**底层已经在跑**（轮廓 → 墙 → 房间 → 屋顶，全部有断言）。
> 缺的是**玩家入口**：现在是自由画轮廓，将来要包一层「模板 + 参数」。
> Willow 2026-09-12 已定：**建筑暂缓**，先用固定房子把地形/农业/昼夜/光影跑通。

## 六、项目架构原则

**数据驱动**：禁止大量 `if npc_type == farmer`。

> **本项目现状**：9 张 `data/*.gd` const 表，**反模式检查为零命中**。
> 数据格式**冻结为 GDScript const**（Core Architecture V1.0 ②）——
> 编译期类型检查、解析失败立刻报错、导出构建直接可用。
> 翻案需要一个**能被说出名字的理由**（mod 支持 / 热重载 / 非程序员编辑），
> 「JSON 比较标准」不是理由。

**关于目录结构**：原文建议 `systems/ actors/ content/ simulation/`。
本项目现为 `world/ character/ data/ building/` —— **同一个原则（按功能域），不同的名字**。
在 Godot 里重命名目录有真实成本（`res://` 字符串、`.uid`、类缓存），收益接近零。
**将来新系统进来时按连贯命名放**（怪物 → `actors/` 是比 `character/` 更准的名字），
**不是现在重命名能跑的东西**。

**关于 Entity + Component**：
**本项目已经是数据驱动的**（`CozyNpcState` + `appearance` 五槽 + 9 张表）。
Core Architecture V1.0 ① 定的是**一个薄注册表**（统一 id + `state_of(id)`），**不是 ECS**。

## 七、要避免的坑

| # | 不建议 | 理由 |
|---|---|---|
| 1 | 一开始做无限世界 | 增加存档/加载/性能/网络负担。先固定区域 |
| 2 | 直接做完整 RPG 框架 | 特色不在战斗，在**家园 × 居民 × 成长 × 冒险** |
| 3 | 过早做复杂联机 | 家园=访问他人世界、副本=多人合作，但**第一版单机** |

**联机的三条架构约束**（现在不实现，但数据结构里要留，见总纲 §82）：
世界归属 / 存档边界 / 玩家离开时家园是否继续模拟。

## 总结

核心循环：

```
建设家园 → 培养居民 → 进入副本 → 获得资源装备 → 强化家园 → 探索更危险区域
```

所有系统采用 `Data Driven + Procedural Generation + Template Based Design`。

**最重要的一条**：**基地里的居民，就是你冒险世界的一部分。**
培养铁匠 → 他做传奇武器 → 你带着它进魔域 → 带回材料 → 升级村庄。
**这个闭环把「家园」和「副本」从两个游戏变成一个** —— 任何取舍优先保住它。
