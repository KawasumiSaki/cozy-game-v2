## 一句话
蓝图存**墙的多边形（outlines）**不存房间，所以地牢"只是另一批墙" ——
而这句好听话里**唯一不免费的一步**，就是把多个 outline 对彼此解析成**一套不重复的墙**。

### DG-02 蓝图契约（2026-09-14）

**单元 13 例 67 检查**（`tests/unit/test_dungeon_blueprint.gd`）：

```
[cozyunit] dungeon blueprint            13 case(s),  67 check(s)  [OK]
[cozyunit] 11 suite(s), 74 case(s), 894 check(s), 0 failure(s)  [OK]
```

| 用例 | 断言什么 |
|---|---|
| 按文档的写法写出来就能解析 | `id` / 两条 outline 原样到达 |
| **往返经过真序列化器** | `to_json()` → `parse()`，坐标逐个相等 |
| **往返经过真文件** | 走 `FileAccess` 落盘再读回 —— 不变量原文要求的是这个 |
| **文档里全是 JSON 自己的数字** | 重新 `stringify`+`parse` 后，outline 仍是 list、坐标仍是 number |
| **outlines 仍然推出两个房间** | 蓝图 → `layout()` → 7 道墙 / **2 个房间**（不是合并的 1 个） |
| 更新的版本被拒 | 不按 v1 读 —— 否则会**静默丢掉**新版本加的东西 |
| 没有 version 被拒 | 不默认版本，否则每次升版都是对旧档的静默误读 |
| `links` / `spawns` / `content` / 未知键被拒 | 拒绝理由**点名**该字段，并说明它为什么不能进 |
| 自交 outline 被拒 | 用的是**建筑管线自己的那句话**（`CozyOutlineGenerator.reject_reason`） |
| 畸形 outline 被拒 | 奇数个坐标 / 非数字 / 不是 list / 空 —— 一条坏的拒整份文档 |
| 被拒的文档**不产出蓝图** | 跳过 reason 的调用方拿不到半成品 |

**牙齿是被制造出来的，不是声称的**（`--script res://tests/unit/run.gd` 逐条改坏再跑）：

```
to_dict 改成吐 PackedVector2Array   → 6 处红（含"真文件"那条）
_unknown_reason 放行一切            → 11 处红
_version_reason 放行更新版本        → 5 处红
from_dict 丢掉 outlines             → 5 处红（房间数 0 ≠ 2）
parse() 改回 JSON.parse_string      → 断言全绿，**但日志里多出 1 行 ERROR**
```

**最后那条值得单独记**：`JSON.parse_string` 遇到坏 JSON 会**打印**。
它的症状不在断言里，只在日志里 —— 也就是说，
"拒绝一个坏文件"当时长得像"构建坏了"。已改走 `JSON.new()`（返回错误码，不打印）。
**它唯一的证人就是那条 `0 ERROR`。**

## 为什么"存墙"这条修订是对的（实测）

设计文档 §三.3 把蓝图从 `rooms` 改成了 `outlines`，理由是第一条不变量
（`Rooms are DERIVED, never authored`）。实测支持它，并且**多给了一条理由**：

`outlines` 走一遍现有管线，房间 / Portal / RoomGraph / 导航 / 屋顶 / 遮挡 / 存档
**全部自动派生**，一条断言都不用改。地牢确实"只是另一批墙"。

**但有一个静默的坑，文档没写**：两个 outline 并排时，
`CozyOutlineGenerator.plan()` 会给每个 outline 各封一次口，共享边**发两遍**，
平面面遍历随后把两个房间**合并成一个** —— 不报错、不告警。
按最朴素实现，整座地牢会变成一个房间，而且看起来像成功了。

已写进 `docs/INVARIANTS.md`，并由此得到一条更强的结论：
**`links` 根本不必存** —— 哪两个 outline 相接、接在哪一段，是几何上可推导的。
存它就是把推导结果写进文件，运行时推导出来的那一份永远是对的，两份必然漂移。

## ⚠️ 契约的三条拒绝，**这是本轮唯一的口径决定**（2026-09-14）

`dungeon_blueprint.gd` 把设计文档 §三.3 示例里的三个字段**全部拒收，并各给一句理由** ——
不是"读进来丢掉"。这个区别就是全部：

> **一个"收下但从不读"的字段，从作者那一侧看，和一个真在工作的字段长得一模一样。**

本项目为"声明了没有消费者"已经付过 7 次代价，所以宁可拒收：

| 字段 | 拒收理由 | 性质 |
|---|---|---|
| `links` | 哪两个 outline 相接、接在哪一段，**由几何推导** | **永远不存**（不是"还没做"） |
| `spawns` | 还没有 spawn 词汇表可以拿它去校验 | 等系统来了**连同校验一起加进格式** |
| `content` | 还没有 content/掉落表词汇表 | 同上 |

**🔵 要 Willow 确认的一句**：§三.3 的示例里 `links` 还在，而契约现在**拒收**它 ——
`links` 那条是"永远"不是"暂时"，另两条是"暂时"。**若不同意，说一声，改一个函数就行。**

版本策略同理：**更新的版本拒收，不尽力读** ——
尽力读会把它认识的字段收下、把新版本加的东西丢掉，症状是地牢**悄悄少一间房**。
更老的版本该走迁移步骤（照 `save_manager.gd` 的先例），但**现在 1 下面没有东西**，
所以**不建只有一节、没有数据的迁移链** —— 那正是本文件拒收两个字段的同一个理由。

### `to_intents()` —— 生成器（2026-09-14）

**单元 13 例 40 检查**（`tests/unit/test_dungeon_layout.gd`，与墙联合同一个套件）：

```
[cozyunit] dungeon layout               13 case(s),  40 check(s)  [OK]
[cozyunit] 17 suite(s), 140 case(s), 2168 check(s), 0 failure(s)  [OK]
```

| 用例 | 断言什么 |
|---|---|
| **转换是有去无回的** | 一道墙一个 intent，每一扇门都变成一个 `CozyOpening` —— 附一条**金丝雀**（`wanted == 1`），否则「0 扇门、0 个 opening」和「转换正确」长得一样 |
| **plan 轴 → Godot 轴，且楼层高度传下去了** | `Vector3(a.x, base_y, a.y)`，两端都验 |
| **门落在墙的正中** | 6 m 的共享边上，`offset` 必须是 **3.0**。读旧约定会得到 **2.25** |
| **intent 走真实 State → 还是两个房间** | 不是从 intent 反推，是喂进 `CozyBuildingState` 再拿 `centreline()` 去检测 |

**🔴 这一步顺手修掉一个会静默偏移的真 bug**：`walls()` 发的是门洞的**近端边**
（`mid - width * 0.5`），而 `CozyOpening.offset` 的语义是**中心**
（`CozyOutlineGenerator` 用的是 `edge_len * 0.5`）。直接把一个当另一个用，
**每一扇门偏 0.75 m** —— 偏到足以出事，偏得不足以看起来不对。
旧字段**没有消费者**，所以约定在源头统一，而不是在唯一的调用点加一句
`+ width * 0.5`（那种算式没有人会去质疑）。

**改坏实验（5/6 红）**：近端边当中心 · `walls()` 退回近端边 · 轴交换 · 忽略 `base_y` ·
门宽写死 1.0 —— 全红。第 6 条「opening 不带上去」**锚点没对上（SKIPPED）**，如实记。
