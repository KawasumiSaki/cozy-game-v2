## 一句话

**装备面板画身体有的 13 个位置，背包画背包有的格子，中间的三个动词不会弄丢东西。**

## Willow 的原话（2026-09-15）

> 装备面板和背包最好是可以互动的，就是你在装备面板右键装备可以显示脱下和卸下，
> 脱下就是放到背包里面，卸下就是扔到地上。**现在还不用做角色身上真的穿了装备。**

拆成四条：13 个槽 / 背包画格子 / 右键已装备的 → 脱下+卸下 / 背包 → 装备。

## 布局：**一个右栏，不是两个角**

两个面板是**一件事的两半** —— 在一个里把剑脱下来、看着它出现在另一个里，
就是 Willow 说的"可以互动"的全部意思。锚到同一个角会是"一个面板把字压在自己身上"，
所以它们进同一个 `VBoxContainer`（`gear_panel` 在上，`pack_panel` 在下），
两个都由 **Inventory** 这一类打开。

⚠️ **右栏设 `MOUSE_FILTER_IGNORE`** —— 否则栏内的空白处会把点击吞掉，
世界在面板下面收不到右键。面板自己仍然是 `STOP`。

## 格子是**位置**，不是计数

`CozyItemContainer` 和 `CozyEquipment` 存的都是**数组**，两边都写了理由：
第二枚戒指进第二个位置，稀疏列表会把两枚都塞回第一个。
所以面板画的是**全部位置**（空格也画），而不是"手上有的东西" ——
**空格子本身是信息**：背包还有空位，还是少了一格，这是两件事。

`CozyItemSlot` 是一格的部件（`Panel` + 右键），两个面板共用。
**左键故意什么都不做**：还没有拖拽，一个会响应左键的格子会像"能用"。

**格子显示的是 `appearance_name()`** —— 幻化过的物品显示它**看起来像什么**，
而 tooltip（`describe()`）说它**实际是什么**。
这个方法当初就是为这里写的，直到面板出现之前**一个调用者都没有**。

## 三个动词，两个会弄丢东西

| 动词 | 从 → 到 | 会失败吗 |
|---|---|---|
| **脱下** `stow` | 身上 → 背包 | **背包满 → 拒绝**，东西**留在身上** |
| **卸下** `unwear` | 身上 → 地上（`EQ-01` 那条路） | 不会（地上永远放得下） |
| **装备** `wear` | 背包 → 身上 | 顶下来的那件**回到背包** |

**两个交换是这游戏里唯一能让物品"消失"而不只是"出错"的地方。**
两次都发生在 `CozyPlayerState` 上，因为只有它同时拥有背包和身体：

**① `stow`：先问背包、再脱。** 反过来的顺序 —— 先脱，然后发现没地方放 ——
结局是**既不在身上也不在背包里**，玩家看见的只是"我的剑没了"。
而且状态**是自洽的**：丢完之后一切正常，只是少了一样东西，**断言看不出来**。

**② `wear`：顶下来的那件一定能放回去，因为腾出来的正是它要的位置。**
这不是运气，是一条性质，所以**从背包里换装永远不可能丢东西**。
`equip()` 返回被顶下来的那件，就是为了让调用者能决定；这里唯一的决定是"放回去"。

```gdscript
if displaced != null and bag.add_item(displaced) < 0:
    push_error(...)   # 够不到；够到就说明容器和容量表吵架了
```
**写成 `push_error` 而不是返回值**：这里没有"正确地继续下去"的方式 ——
一件哪儿都不在的物品，是玩家看不见、说不清、也拿不回来的那一种失败。

## 卸下要扔到**前面**，不是脚上

```
TOSS_DISTANCE 1.4  >  CozyDroppedItem.PICKUP_RADIUS 0.6
```

**这是那个数字存在的唯一理由**：掉在玩家自己位置上的东西**按定义就在拾取半径内**，
下一帧会被自动捡回来，那个按钮看起来就是坏的。
扔向**前方**（`camera.ground_forward()`，和 W 键同一个方向）而不是侧面，
因为那是玩家正看着的地方。

## 布局也有一条断言（**headless 唯一能验"面板在不在屏幕上"的方式**）

面板会不会被画到屏幕外，本来是只有截图才看得见的事：
**里面的每个格子都在、都对、都点不到**，玩家报的是"面板坏了"。

`Control.size` 要等一次 layout pass 才有，而且**容器会跳过隐藏的子控件** ——
所以这条必须**两段式**：第 600 帧的 stage 只负责打开面板，第 640 帧的才量。

**而这条断言我第一版写错了，是改坏实验抓出来的**：

```
「面板不小于它需要的最小尺寸」   → 恒真（容器不会把子控件摆到最小尺寸以下）
「面板装得下它所在的栏」         → 恒真（栏会长大来装下子控件）
「都还在窗口里」                 → 真的
```

实测：格子 68→88 px 时，**栏从 300 自己长到了 354，前两句照样绿**，
而面板已经跑到 1280 宽窗口的外面去了 —— **正是这条断言要抓的那个失败，报的是 `[OK]`。**

tell 是**句子是用什么写的**：那两句在描述布局规则**会做什么**，
**凡是能从规则推出来的都不可能是规则被违反的证据**；
活的那句**点名一个失败**（"右手边那列格子不在屏幕上"）。

修法留下的两句都是能假的：**内容需要的宽度超过了这个文件自己声明的宽度** /
**带着这个溢出，整栏跑出了窗口**。

## 改坏实验（`D:\cozy\tools\mutation_check_panels.py`）

**13 条，13 条全部见红。**

| 改坏 | 结果 |
|---|---|
| 一个 kind 只画一格（不是每个位置一格） | 红 |
| 背包格子数跟着"手上有几件"走 | 红 |
| 每个格子都画第一个位置 | 红 |
| 格子显示"是什么"而不是"看起来像什么" | 红 |
| Inventory 类别忘了开装备面板 | 红 |
| 卸下的东西掉在脚上 | 红 |
| 脱下忽略满背包（冒烟 + 单元） | 红 ×2 |
| 装备时把顶下来的那件丢掉（冒烟 + 单元） | 红 ×2 |
| 背包里任何东西都能穿 | 红 |
| **格子加宽到栏装不下** | 红 ← 见上 |
| **面板声明宽度小于内容** | 红 ← 见上 |

**四条断言量的是别处量不到的事**（写在这里，因为它们是这一轮真正在做的事）：

1. **面板画的是不是位置** —— 数**空格子**，那个数没有别的东西会产生
2. **13 个格子也是"全画在第一个格子"的画法** —— 所以问的是**哪一个**格子收到了剑和戒指
3. **脱进满背包**必须拒绝、留在身上、并且**说出为什么**
4. **卸下要落在拾取半径外** —— 顺带把两个常数的关系也钉住
