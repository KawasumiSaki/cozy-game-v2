# 调研 · 有没有能直接套用的开源游戏系统

> **日期** 2026-09-14 ｜ **范围** 模拟经营 / 技能树 / 等级·经验 / 装备数值
> **起因** Willow：去找点开源的 skill 或者别人做好的游戏系统，看看能不能直接套用。
> **结论一句话** **没有任何一个能直接套用。三个方向全部指向"自己写更便宜"。**

## 筛选标准（先说清楚，免得读成一堆用不上的推荐）

Core Architecture V1.0 **已冻结**，明文 **不做 ECS、不做 EventBus、数据表不用 JSON/Resource**。
所以判据不是"最流行的"，是**能不能塞进现有缝里、不用改架构**：

| 金子 | 负债 |
|---|---|
| 纯数据 + 纯函数 | 自带 autoload / 单例 |
| 不启世界就能测（无场景树） | 长在场景树上、按节点 tick |
| `const` 字典 + 静态函数 | `.tres` / JSON 数据格式、自带节点基类 |
| 确定性（播种随机） | `randf()`、状态存在 View 里 |

## 一、装备 / 数值系统

| 项目 | 许可 | 数值聚合能力 |
|---|---|---|
| **GodotPrompter `stat-modifiers.md`** | MIT | ★ **最好的规格**：ADD → MULTIPLY → OVERRIDE → CLAMP，**按来源记账** |
| ClarkWain `godot-arpg-kit` | MIT | `(base + Σflat) × (1 + Σpercent)`，能用但长在 `Node` 上 |
| Wyvernbox inventory | MIT | 只有平铺求和，无乘法层 |
| gloot / expressobits / OctoD / Lootie | MIT | **完全没有数值系统** |
| StatHub | MIT | **C#，排除** |
| GD-Agentic-Skills | ⚠️ **LGPL-3.0** | **传染性许可，不能用** |

**值得抄的只有两块，约 150 行：**

1. **GodotPrompter 的四遍结算 + `source` 记账**（MIT，纯文档零依赖）
   最值钱的是语义：**同一来源再次添加 = 刷新，不是叠加。**
   这正是装备槽需要的 —— 换一件装备不会把上一件的加成留在身上，
   **省掉一整类"脱了装备属性还在"的 bug。**
2. **Wyvernbox 的词条曲线**（只抄词条）：
   `值 = init + linear × level + quad × level²` + 权重抽词条 + 数量/等级区间。

**没人解决条件修正**（"当 HP < 50% 时 +30% 暴击"）。要做只能自己设计。

### 🔴 待拍板：百分比怎么叠

| | 算法 | +20% 与 +10% 并存 |
|---|---|---|
| GodotPrompter | 各自相乘、依次施加 | **×1.32** |
| ClarkWain | 百分比先求和、再一次性施加 | **×1.30** |

**两种不同的游戏。**前者是暗黑/流亡黯道那套 "more vs increased"，后者是线性叠加。
**后期差距极大**（10 个百分比词条能差一倍）。**这是设计决定，不是实现细节。**

## 二、殖民地模拟 / 工作分配 AI

**Godot 侧没有一个能用。** beehave（3.3k★）和 limboai（3.0k★）都是 MIT、都在积极维护、
**都不可用** —— 节点驱动、长在场景树上，一个 NPC 一个节点，
采用即破坏"不启世界就能测"。

> **Godot 资产库用 "colony" 搜，零结果。**
> **没有殖民地模拟的工作系统这个东西 —— 这个"没有"本身就是结论。**

### 🔴 但在**我们自己的代码里**找到三个真缺陷

| # | 位置 | 问题 |
|---|---|---|
| ① | `npc_agent.gd:244` `_acquire_job()` | **只按距离挑**，无优先级。居民会路过紧急的活去干更近的琐事 |
| ② | `npc_agent.gd:92` `want_point_type() -> String` | **结构性堵点**：返回单个 String，**写不出"先做饭，没有就搬运"** |
| ③ | `npc_agent.gd:324` `"spot taken"` | **占位竞态**：走到了才发现位子被占，那趟路白走 |

**② 直接卡着资源线**：耕地 / 种田 / 挖矿 / 砍树是**四种活竞争一个居民**，
而现在的签名**表达不了这件事**。作物做出来，居民也只会挑最近的那个。

### 值得抄的三个算法（算法，不是代码）

1. **RimWorld 的四键字典序**：工作类型优先级 → 列序 → **WorkGiver 自然优先级** → 距离。
   `jobs.gd` 每行加一个 `priority: int`，`want_point_type()` 换成**有序数组**。
   可直抄的真实数字（**约 10 倍跨度**，这就是"先干紧急的"不用写特例的原因）：
   ```
   搬运：补弹 150 ｜ 加油 140 ｜ 卸货 130 ｜ 剥尸体 100 ｜ 一般搬运 15 ｜ 合并堆 5
   清洁：扫雪 10 ｜ 清污 5
   建造：修故障 120 ｜ 拆装 110 ｜ 盖屋顶 100 ｜ 送料 60 ｜ 拆除 50 ｜ 修理 40 ｜ 打磨地板 20
   ```
   **RimWorld 是拉模型，我们 `_acquire_job()` 也已经是拉模型** —— 这是**换比较器**，不是重写。
2. **Widelands 防饿死队列**（约 20 行）：基准 低2/普通4/高8，工地 +2 仓库 −2，
   最后一程 +2，**每轮没选上 +1、上限 16**。
   **那个上限就是保证**：高优先级源源不断时，最低的活最多等约 15 轮。
3. **滞后 + 动量**（治反复横跳）：当前任务 **+25%**（momentum）；
   挑战者要赢过现任 **Δ ≈ 0.15 × 平均分** 才准换。两个 float。

**唯一值得读的仓库** `grenzmark`（MIT，Godot 4.6.3）：
`core/` 纯模拟无场景树、`game/` 只渲染、固定 30Hz、禁未播种随机、headless 约 735 断言
—— **架构和我们几乎一样**。**但它的工作分配是 Settlers II 搬运工模型，没有优先级系统**
（它自己的 ROADMAP 都写着未完成）。**读它的分层与测试脚手架，别读它的工作分配。**

## 三、技能树 / 等级系统

**Godot 4 没有可复用的经验/等级库。**
资产库 `experience` / `progression` / `talent` **各 0 条**；`skill tree` 只有 2 条（都是绘图工具）。
GitHub "talent tree plugin" **0 条**。

唯一架构兼容的是 `NicolasIRAGNE/GodotAgnosticSkillTree`（MIT / 4.7 / 无 autoload / 有 headless 测试），
但 **0 star、单次提交、`.tres` 数据模型**。**只抄两个设计，别抄代码**：

1. **`get_unlock_block_reason(id) -> String` 而不是 `can_unlock() -> bool`**
   —— 返回**为什么**被挡住，让 Solver 的"理由"变成**可断言的值**。
   （这正是本项目已经在用的形状：`CozyOutlineGenerator.reject_reason`、`CozyDungeonBlueprint.reject_reason`）
2. **`set_unlock_policy(validate, commit)`** —— 两个注入的 Callable，
   正是 Intent → State → Solver 的接缝：**图归插件，货币和事务归项目**。

**自己写约 150–250 行 + 一个 `CozySkillTreeDefs` 字典。**

### ⚠️ 两个推翻前提的发现

**① 等级/经验系统 —— 我们**已经**有了。**
`data/skills.gd`（`CozySkills`）：10 个技能、`MIN_LEVEL 0` / `MAX_LEVEL 20`、
`Passion` 枚举含 `PASSION_MULTIPLIER`(0/1/2/4)、`clamp_level()`、`can_be_assigned()`、`blank_skills()`。
**已经是 const 字典 + 纯静态函数的路子，还有断言。不需要任何库。**

**② 技能树在总纲里是**范围外**的。**
`00-架构总纲/V2.2-技术架构总纲.md:112` 明写：
> 技能树、死亡与复活、多 NPC 管理、居民装备 —— **一行都没有。**

**所以把技能树拉进来，是架构文档层面的决定（按项目规矩要停下来问 Willow），
不是"去买个库"的决定。**

## 三个方向共同的结论

> **每一个库的价值，恰好都集中在被我们冻结掉的那部分** ——
> autoload、自带数据格式、自带节点基类、状态存在 View 里。
> 把它们剥掉之后剩下的，是一份前置列表、一个环检测、一个"为什么不能解锁"的函数。

**自己写比套用便宜。** 时间预算：装备数值约 1 天；工作优先级改造主要是换比较器 + 加一列；
技能树 150–250 行 —— 前提是总纲那条"一行都没有"先被正式解冻。

## 🔵 四条版本事实（4.7 相关，直接影响决策）

1. **Jolt 现在是 4.7 的默认 3D 物理引擎**，而**我们的 `project.godot` 没有覆盖** →
   **我们在用 Jolt + GL Compatibility。**
2. 🔴 **一个活的回归（GH #120193）**：在 `Area3D.body_entered` 回调里设
   `process_mode = PROCESS_MODE_DISABLED`，会**永久杀掉那两个实例之间的碰撞检测**。
   这条正好打在"用 process_mode 关掉一片区域"和 Area3D 打点这两件事上。
3. **`SceneTree.paused` 会全局停掉物理服务器** —— `PROCESS_MODE_ALWAYS` 能拿到 `_process`
   但**拿不到物理**。而且它**跨场景保留**。所以**"暂停副本让家园继续跑"用暂停做不出来。**
4. 鼠标/键盘设备号从 `0` 变成 `32` / `16` —— 硬编码 `0` 的插件会**静默失效**。

## 一、UI

**生态结论：不是缺东西，是缺"不带架构"的东西。**

| 项目 | 许可 | 结论 |
|---|---|---|
| **ThemeGen** | MIT | ✅ **可用（当工具）** —— `extends EditorScript`，**结构上不可能**跑进正式游戏；它吐一个 `Theme` |
| **Dockable Container** | **CC0** | 🟡 条件可用：无 autoload、不强调主题、布局树是 `Resource`（**真的能不启世界测**）。但**没在 4.7 上验过**，且**标签图标是 TODO** |
| Monitor Overlay | MIT | ✅ 开发者模式的性能指标，直接可用 |
| limbo_console / godot-debug-menu | MIT | 读设计，**是 autoload** |
| **GDSS** | MIT | ⛔ **响铃警告**：它会**往你的 `project.godot` 里写 autoload**，自带 `.tgdss` 格式，11,543 行 |
| UIFlow | MIT | ⛔ 强制基类 + 全局门面 + **EventBus** + autoload —— 四项全犯 |
| Wyvernbox Inventory | MIT | 只读数据层；**它的 GUI 处理器直接改背包** |

**🔴 最重要的发现：生态里每一个控制台插件都是单例**（查了六个，都在插件源码层确认）。
控制台按定义就是全局命令表，所以这不是市场空白。
**而本项目架构下的逃生舱**：`class_name DevCommands` 上的 **`static var`** ——
`static var` 是**按类**的、不是按场景的，所以**不引入 autoload 也能全局注册命令**。
**这是一个政策决定，应该被明确做出来，而不是悄悄绕过。**

**设计参考**：**Pixelorama**（MIT，**今天还有提交**，七个完整主题包，正确使用 `base_type` 继承）。
它和 Dockable Container **两个独立实现收敛到同一个布局树形状** —— 这是"这个形状是对的"的强证据。

`main.gd:1160 _build_hud()` / `1187 _on_hud_tool_selected(i)` —— **当前工具是从 UI 回调设的**。

## 二、近战战斗

**没有可用的 Godot 4 3D 近战插件** —— 全是 2D / autoload / 整个游戏模板 / 许可陷阱。

### 🔴 打点方式有一个明确答案（这才是真正的交付物）

**Area3D 重叠 —— 在确定性上输，在可测性上输得更多**，两个各自独立的失效：

- `get_overlapping_areas()` 返回的是**每物理步刷一次的快照**
- `area_entered` **只在"进入"那一刻触发** —— 所以如果你在挥砍第 6 帧才打开打点盒，
  **而目标已经在盒子里，信号根本不会发，这一击静默丢失**
- 常规的绕法（激活时重扫）直接撞上快照问题，需要**延迟第二次扫描** ——
  于是"命中发生在第 6 帧"**不再是一个事实**
- 最差的是可测性：要活场景树 + 物理服务器 + 层 + 形状，而**失效模式全是静默空操作**

**✅ 显式 `intersect_shape` / `ShapeCast3D` + `force_shapecast_update()` —— 赢。**
同步、同帧给出当前状态的答案。而且 `target_position = Vector3.ZERO` + `force_shapecast_update()`
**在 `enabled == false` 时也能用** —— 正好是"打点盒只开 12 帧"这个场景。只在激活帧付费。

**⛔ 动画驱动激活 —— 不能当权威。** `AnimationPlayer` 在**渲染帧**推进，而打点在 `_physics_process` 里跑，
所以开盒那一帧**取决于帧率**（真的会漂）。更糟：方法轨**没有任何不启世界的方式**回答
"`attack_02` 在第几帧激活"——答案在一个 `.tscn` 里的 `Animation` 资源里，**我们的 136 条断言够不到**。
**正确框架：动画是"帧数据表"的视图，不是权威。**

**⛔ 顿帧绝对不能用 `Engine.time_scale`**（godot#24334：它会改物理 delta，
让结果"剧烈变化"）。**用一个整数计数器压制本地战斗时钟的推进** —— 零成本、可断言。

### 该实现的形状（约 300 行纯逻辑 + 一个 10 行的脏接缝）

```
Intent  { tick, move_dir, buttons: {light, heavy, block} }
State   普通 Dictionary：attack_id, frame_in_attack, phase, combo_index,
        combo_window_ticks, iframe_ticks, hitstop_ticks, block_state,
        block_held_ticks, already_hit_ids, facing      ← 无节点、无 _process
Data    CozyCombatDefs：const ATTACKS（windup/active/recovery/damage/hitstop/
        combo_next/combo_window/reach/box）· const GUARD（reduction/chip/
        parry_window/stagger）                          ← 现有 CozyXxxDefs 约定
Solver  四个纯静态：active_window(def) / can_start() / apply_hit() / resolve_hits()
        apply_hit 是 i-frame 与格挡的**全部答案**，顺序：
        i-frame → 格挡/招架（看朝向）→ 伤害 → 设 i-frame/顿帧/连招窗
Node    _physics_process 推进一 tick，调 solver，
        需要时调 _shape_query()  ← 整个系统唯一碰世界的地方，也是唯一需要打桩的
```

**约 40 条不需要世界的断言**：`active_window(...) == Vector2i(6,12)`；
推进 5 tick → `WINDUP`，再 1 tick → 要查询；重复候选 id → 恰好命中一次；
`iframe_ticks=4` → 零伤害且不开连招窗；`block_held_ticks=3` → 招架；
`block_held_ticks=40` → `damage == int(8*0.4)`。

**证据**：Card Combat System 证明了这个形状可行（无头、无场景、无 autoload、
`class_name` only、418 条 GUT 测试、逐位可重放）—— **但它是 AGPLv3，只能读结构，代码自己写。**

## 三、两个世界

**生态结论：每一个场景管理插件都是 autoload。**
这不是巧合 —— `change_scene_to_file()` 会**删掉退出中的那棵子树**，
所以生态对"状态住哪"的统一答案就是"住在不在场景里的东西里"。

### 🔴 "家园在副本期间还跑不跑" —— 三个答案

| | 做法 | 结论 |
|---|---|---|
| **(a)** | 真的 tick 模拟，家园留在树里 | **最差**。`SceneTree.paused` 全局杀物理且跨场景保留；跑 `_process(delta)` 则结果取决于帧率。**可测性为零** |
| **(b)** | **回来时补算（离线进度）** | ✅ **确定性完美、无头可测完美**。状态是普通数据，`advance(state, ticks_elapsed)` 一把推过去。20 分钟副本 = 1,200 tick，白送。**真正的代价是设计**：`advance` 要**吐一份事件日志**（"作物 X 在第 812 tick 熟了"），回来才能讲给你听 |
| **(c)** | 暂停世界 | 让"不在时作物会长"变成谎言 —— 除非特例处理，而那时你已经把 (b) 写坏了一遍 |

**⛔ 不要用 `SceneTree.paused` 来冻结家园。**

### 该实现的形状（仓库里已经有一大半）

- **节点树**：`main.gd` 是**常驻根，永不替换**（`change_scene_to_file` 会把 `main.gd` 自己删掉）。
  下面挂 `WorldRoot`（**唯一交换的东西**）/ `PlayerRig` / `CameraRig` / `UI`。
  进门时释放 `WorldRoot` 的子节点、按状态实例化另一个世界。
  **`CozyPortal` 已经是这个抽象** —— 副本的门只是另一个 `Kind`。
- **什么活下来**：一个普通数据对象（`tick` / `rng_state` / `seed` / 背包 / 每块地的作物记录 /
  副本进度 / **居民只存"定义 id + 参数"，绝不存节点引用、绝不存位置**）。
  `CozySaveManager` 已经在强制这条"只存事实"的纪律。
- **推进**：一个 `static func advance(state, n) -> Array[Dictionary]`。
  `main.gd` 把真实 delta 换成整数 tick 再调它 —— **在家是 `n=1`，从副本回来是 `n=elapsed`，同一次调用。**
  `CozyTimeSystem.advance()` 已经是这个形状。
- **🔵 居民根本不需要被模拟**：`static func position_at(def_id, tick, seed) -> Vector3` ——
  **时间索引查询**（Stardew 模型）。**这把居民从持久化问题里整个删掉了。**
  我们的 `CozySchedule`（小时 → 活动，纯 `const` 表）已经是这前半段。
- **把墙钟隔离**：`ticks_for_elapsed(seconds, ...)` 是 `advance` **之上**的策略函数；
  模拟层**永不读 `Time.*` / `delta`**。这样"家园继续模拟了吗"变成一个**可以改、且不用碰模拟层**的决定。

**设计参考**：**Windowstead（GPL-3.0，只读）** —— `RefCounted` 的无场景 tick 模拟、
整数 tick、可设的 RNG 种子、带修订号的事件日志、不启世界的无头 tick 测试。
**和我们的分层独立收敛到同一形状。** 但它**没有**离线补算（它是常驻桌面应用）。

## 三条路共同的结论

> **没有值得套用的。而该实现的形状，仓库里已经有 70%。**
> 真正新的只有三样：`CozyCombatDefs`/`CozyCombatSolver` 一对、
> 一个 `HudSnapshotter`、一个 `advance(state, n)` 补算函数 ——
> **全是纯 GDScript `class_name` 文件，正好贴着现有约定。**

**许可红线（只读，绝不抄代码）**：Card Combat System（**AGPLv3**，最好的战斗架构）、
Windowstead（**GPL-3.0**，最好的世界模拟设计）、NeonSceneRunner / Revengate（GPLv3）。
